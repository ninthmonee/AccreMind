

# AI 研发知识基座 思路 V1版本

## 一、产品概述

### 1.1 产品定位

AI 研发知识基座是一套服务于 AI 辅助编程场景的**团队知识工程基础设施**。它通过系统化的知识分层架构、信号驱动的智能沉淀机制、云端统一配置下发和多来源知识汇聚，让 AI 编码助手从"通用大模型"进化为"懂业务的团队研发伙伴"，实现"AI 越用越懂业务"的正向飞轮。

### 1.2 核心问题

当前 AI Coding 工具（Cursor、Copilot、Claude Code 等）本质上是**个人助手**，存在三个结构性缺陷：

| 问题         | 表现                                          | 根因                         |
| ------------ | --------------------------------------------- | ---------------------------- |
| **知识孤岛** | 超级个体的经验锁在本地配置中，无法惠及团队    | 存储本地化，作用范围单用户   |
| **经验流失** | 踩过的坑反复踩，架构决策每次重新推导          | 无自动沉淀机制，依赖人工维护 |
| **配置混乱** | 切换仓库/业务域需手动配置规则，新人上手门槛高 | 配置跟人走而非跟项目走       |

### 1.3 产品愿景

**超级团队 = 超级个体 × 知识共享 × 智能沉淀**

将团队在特定业务领域积累的**领域模型、架构决策、最佳实践、已知陷阱、业务流程**沉淀为永恒的团队资产，让每次需求交付都是一次知识积累，让每个新成员"站在前人肩上"。

### 1.4 核心设计原则

| 原则                         | 含义                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| **工作流是手段，知识是目的** | Harness 工作流会随模型迭代而重构，但领域知识永恒             |
| **信号驱动 > 全量沉淀**      | 用 1% 的"踩坑会话"提炼 90% 的价值，不做无差别全量存储        |
| **云端存储、本地零负担**     | 所有知识存储在云端，本地仅一个 gateway.md（~200行），通过 MCP 按需获取 |
| **量变引发质变**             | 知识消费者是 AI 而非人，先追求覆盖面，靠 AI 召回时自动筛选   |
| **云端统一 > 本地分散**      | 配置管理上云，按仓库自动匹配，零配置开箱即用                 |
| **业务隔离 > 全局混杂**      | 按业务域物理隔离知识，避免跨域污染                           |
| **闭环验证 > 单向入库**      | 知识从沉淀到消费到验证形成完整闭环，持续迭代                 |

### 3.2 模块关系与数据流

**核心架构原则：云-端分离。** 所有知识经验文档存储在云端，本地环境只部署一个轻量的"知识网关"文档（`knowledge-gateway.md`），告诉 LLM 在需要时如何通过 MCP 协议调用云端知识库。本地不拉取、不存储大量知识文档。

```plain

                              │  │  · MCP Server 地址   │  │

                              └─────────────────────────┘

知识消费流程：
  1. LLM 遇到问题 → 读本地 knowledge-gateway.md（~200行）
  2. 网关指导 LLM 调用 MCP search-knowledge 工具
  3. MCP Server 在云端检索，返回精准结果（非完整文档）
  4. LLM 基于返回结果生成答案

知识沉淀流程：
  1. 工作流 ARCHIVE 阶段 → 本地生成知识条目
  2. 通过 MCP ingest-knowledge → 推送到云端
  3. 其他开发者本地无需更新，下次查询自动获取
```

## 四、知识分层架构（核心设计）

### 4.1 五层存储架构

知识按**共享边界和生命周期**分为五层，从个人到团队到项目逐层扩大：

| 存储层        | 名称     | 存储位置                              | 共享范围     | 生命周期       |
| ------------- | -------- | ------------------------------------- | ------------ | -------------- |
| **Layer 0-P** | 个人偏好 | `~/.ai-team/` 本地为主 + 可选云端同步 | 不共享给团队 | 随个人职业生涯 |
| **Layer 0-T** | 团队约定 | 云端 Git 仓库                         | 全团队       | 长期稳定       |
| **Layer 1**   | 技术知识 | 云端 Git 仓库                         | 跨项目通用   | 随技术栈演进   |
| **Layer 2**   | 业务知识 | 云端 Git 仓库（按业务域隔离）         | 按业务域     | 随业务发展     |
| **Layer 3**   | 项目知识 | 云端 Git 仓库（随项目）               | 单项目       | 随项目生命周期 |

**关键设计：知识可向上提升。** Layer 3 的项目知识经判定后自动提升到 Layer 1 或 Layer 2：

```plain
Layer 3 (项目内) → Q1: 是否项目特有？ → 是 → 留在 Layer 3
                 → Q2: 是否通用技术？ → 是 → 提升到 Layer 1
                 → Q3: 是否通用业务？ → 是 → 提升到 Layer 2
```

**Layer 0-P 的铁律：个人偏好永不自动提升为团队知识。** 只有用户执行显式的"分享到团队"操作，才能将某条个人经验手动迁移到 Layer 0-T / Layer 1 / Layer 2。

#### 4.1.1 Layer 0-P 深度设计：个人偏好该存在哪里？

**（1）行业做法对比**

| 工具               | 个人偏好存储                   | 跨设备同步   | 与团队/项目知识的关系                                    |
| ------------------ | ------------------------------ | ------------ | -------------------------------------------------------- |
| **Cursor**         | 本地 `~/.cursor/` + 账号云同步 | ✅ 账号级     | `.cursorrules` 项目级，Memory 个人级，两者隔离           |
| **Claude Code**    | 本地 `~/.claude/CLAUDE.md`     | ❌ 无内置同步 | 全局 CLAUDE.md（个人）与项目 CLAUDE.md（团队）物理分离   |
| **GitHub Copilot** | GitHub 账号云端                | ✅ 账号级     | `.github/copilot-instructions.md` 项目级，个人偏好随账号 |
| **Windsurf**       | 账号云端                       | ✅ 账号级     | `.windsurfrules` 项目级，个人 rules 在账号设置中         |
| **腾讯 AI Team**   | 本地 `~/.ai-team/`             | ❌ 未提及     | Layer 0-P 显式标记"纯本地，不共享"                       |

**行业共识：**

- **个人偏好与团队知识必须物理隔离**——没有任何主流工具将两者混存
- **个人偏好存储位置分两派**：本地派（Claude Code）和云端派（Copilot、Windsurf），Cursor 是混合派
- **跨设备同步是刚需**：Cursor、Copilot、Windsurf 都提供，说明开发者确实需要在多台机器间保持一致的个人体验

**（2）本系统的设计决策：本地为主 + 可选云端同步**

```plain
                    ┌─────────────────────────┐
                    │   Layer 0-P 个人偏好      │
                    │                         │
                    │  💻 主存储：本地           │
                    │  ~/.ai-team/            │
                    │  ├── preferences.yaml   │  ← 编码风格、缩进、命名偏好
                    │  ├── custom-prompts/    │  ← 个人 prompt 模板
                    │  ├── personal-rules.md  │  ← 个人行为规则
                    │  └── local-history/     │  ← 个人会话偏好（不自动沉淀）
                    │                         │
                    │  ☁️ 可选：个人账号云同步   │
                    │  同一开发者的多台设备      │
                    │  自动同步 preferences    │
                    │  不同步 local-history   │
                    │  不同步到团队知识库       │
                    └─────────────────────────┘
```

**为什么选本地为主？**

| 考量维度     | 本地为主               | 纯云端               |
| ------------ | ---------------------- | -------------------- |
| 隐私安全     | ✅ 敏感偏好不出本地     | ❌ 所有偏好上传服务器 |
| 离线可用     | ✅ 无网络也能读取       | ❌ 依赖网络连接       |
| 跨设备同步   | ⚠️ 需额外云同步通道     | ✅ 天然一致           |
| 个人控制力   | ✅ 完全自主，可随时删除 | ❌ 数据在服务端       |
| 团队管理成本 | ✅ 无需管理个人空间     | ❌ 需为每人维护存储   |

**（3）个人空间与团队空间的铁墙**

```plain
┌──────────────────────────────────────────────────────────────┐
│              个人空间 (Layer 0-P) vs 团队空间 (Layer 0-T/1/2/3)  │
├────────────────────────────┬─────────────────────────────────┤
│  个人空间                   │  团队空间                         │
├────────────────────────────┼─────────────────────────────────┤
│  ✅ 从团队知识自动受益       │  ❌ 从不读取个人偏好               │
│  （LLM 通过 MCP 查询团队库） │                                 │
├────────────────────────────┼─────────────────────────────────┤
│  ❌ 永不自动贡献给团队       │  ✅ 自动沉淀 + 自动提升            │
│  ✅ 用户主动"分享到团队"     │                                 │
│     → 经审核后进入团队库     │                                 │
├────────────────────────────┼─────────────────────────────────┤
│  与团队同主题的结论相悖时     │  不关心个人结论                   │
│  → LLM 以团队知识为准       │                                 │
├────────────────────────────┼─────────────────────────────────┤
│  不参与成熟度 / 衰减        │  完整参与 draft→verified→proven   │
│  不参与 Lint 治理          │  完整参与 Lint + 衰减             │
└────────────────────────────┴─────────────────────────────────┘
```

**"分享到团队"是唯一的桥梁：**

```plain
个人踩坑/经验
  │
  ├── 仍在个人空间 → 只有自己受益
  │
  └── 用户执行 "分享到团队"
        │
        ├── 填写分享理由和应用场景
        ├── 自动去个人标识（匿名化）
        ├── 类型自动归类（pitfall / guideline / decision）
        │
        ▼
      进入团队候选池 → 质量评估 → 审核 → 入库
        （与自动沉淀走同样的云端处理流水线，见 5.5.4）
```

**（4）Layer 0-P 存储内容清单**

| 内容分类         | 存储位置      | 是否云同步 | 示例                                                    |
| ---------------- | ------------- | ---------- | ------------------------------------------------------- |
| 编码风格偏好     | 本地 + 云同步 | ✅          | "缩进用 2 空格""偏爱函数式而非 OOP"                     |
| 语言/框架偏好    | 本地 + 云同步 | ✅          | "优先使用 React Hooks 而非 Class""用 dayjs 而非 moment" |
| 个人 prompt 模板 | 本地 + 云同步 | ✅          | "代码审查清单""需求分析提问模板"                        |
| 个人快捷键/别名  | 本地 + 云同步 | ✅          | 自定义 `/fix-lint`、`/gen-test` 等命令                  |
| 本地会话偏好     | 仅本地        | ❌          | 某项目中的临时调试偏好、历史回滚记录                    |
| 个人踩坑草稿     | 仅本地        | ❌          | 尚未验证、不确定是否正确的个人经验                      |

**（5）行业共识总结**

**个人偏好应本地存储（隐私、离线、自主可控），并提供可选的个人账号云同步（跨设备）。个人空间与团队空间之间只有一道门——用户主动"分享到团队"——这道门是单向的、需审核的，且永不反向打开。** 这个设计在行业中被 Cursor（混合派）、Claude Code（纯本地派）和 Copilot/Windsurf（云端派）以不同形式验证过，本系统采纳混合方案以兼顾隐私和便利性。

### 4.2 五种知识类型

知识按"描述的是什么"分类，遵循 MECE 原则：

| 类型          | 定义                                 | 判定标准                    | 示例                                                    |
| ------------- | ------------------------------------ | --------------------------- | ------------------------------------------------------- |
| **model**     | 实体定义、数据结构、关系图           | 描述"是什么"                | "广告计划包含预算/出价/投放时段三个核心字段"            |
| **decision**  | 技术选型、架构决策及理由             | 描述"为什么选A不选B"        | "选择事件驱动而非RPC同步，因广告状态变更需解耦"         |
| **guideline** | 推荐做法(recommend)或禁止做法(avoid) | 描述"应该怎么做/不该怎么做" | "公共模块变更后的兼容性检查清单"                        |
| **pitfall**   | 已知风险、故障模式、排查步骤         | 描述"哪里会出问题"          | "广告预算扣减在高并发下会超扣，需用Redis+Lua保证原子性" |
| **process**   | 业务流程、状态机、操作步骤           | 描述"按什么步骤"            | "广告审核：提交→机审→人审→上线"                         |

### 4.3 三级成熟度 + 自动衰减

知识不是"写完就完了"，它有生命周期：

```plain
draft（新提取，单一来源，置信度 0.5-0.6）
  ↓ 在 ≥1 个工作流中被成功引用
verified（单项目验证，置信度 0.7-0.8）
  ↓ 在 ≥2 个不同项目中被验证
proven（成熟/可信赖，置信度 0.9+）
```

**自动衰减机制**——知识长期不被引用则自动降级：

| 触发条件                         | 衰减动作           |
| -------------------------------- | ------------------ |
| proven 条目 12 个月未被引用      | 降级为 verified    |
| verified 条目 6 个月未被引用     | 降级为 draft       |
| draft 条目持续未引用 + Lint 标记 | 归档，移出活跃索引 |

### 4.4 知识三层分类（业务视角）

从知识来源和维护责任维度，知识分为三层：

| 层次              | 来源                       | 维护方式                | 典型内容                     |
| ----------------- | -------------------------- | ----------------------- | ---------------------------- |
| **组件/平台知识** | 内部组件文档、API 平台对接 | 组件负责方官方维护      | 组件用法、API 文档、最佳实践 |
| **业务领域知识**  | 人工编写 + MCP对接         | 业务域负责人维护        | 业务术语、特殊规范、领域概念 |
| **实践经验知识**  | 信号驱动智能沉淀           | AI自动捕获 + 人工review | 踩坑记录、FAQ、隐性惯例      |

**边界原则**：经验知识库不应充斥本该属于组件官方文档的内容。若某组件基础用法被反复提问，应反馈给组件方补充文档，而非沉淀到经验库。

## 五、智能沉淀能力

### 5.1 会话知识沉淀：信号驱动

#### 5.1.1 核心理念

**不做全量沉淀，只捕获关键事件。** 99% 的会话是"帮我写个按钮"等简单问答，无沉淀价值。真正有价值的知识藏在那 1% "出了问题"的会话里——踩坑、试错、反复调试的过程。

#### 5.1.2 信号识别机制

会话结束时，系统自动识别两类信号：

**关键词信号（从消息文本识别）：**

| 信号类型 | 匹配关键词                                                   |
| -------- | ------------------------------------------------------------ |
| 报错信号 | error、exception、报错、failed、undefined、cannot read、is not a function |
| 否定信号 | 不对、不是、错了、换一个、重新、还原、还是不行               |

**行为信号（从工具调用模式识别）：**

| 信号类型         | 判定条件                             |
| ---------------- | ------------------------------------ |
| 同一文件多次编辑 | 同一 path 出现 >2 次 replace_in_file |
| 工具调用密集     | tool_call_count > 5                  |
| 读后搜索模式     | read_file 后紧跟 search_files        |
| 用户截图反馈     | 消息包含图片 + 否定表达              |

#### 5.1.3 候选筛选流水线

```plain
会话结束 → 信号识别 → 标记"有料"/"无料"
                ↓
         定时任务（每日）：按仓库+分支聚合
                ↓
         候选条件（满足任一）：
         · session_count > 1
         · total_rounds > 10
         · 有报错信号
         · 有否定信号
         · code_change_count > 2
                ↓
         候选池 → LLM 知识提炼
```

#### 5.1.4 LLM 知识提炼

对筛选出的候选会话，使用 LLM 提取结构化知识：

**输入上下文：**

- 基础信息：仓库、分支、会话数、时间范围
- 需求背景：从首个 session 的用户输入中提取
- 会话序列：关键轮次的对话、工具调用、代码变更摘要
- 信号摘要：检测到的错误信息、否定表达

**产出三类知识：**

| 维度         | 定义       | 示例                                                         |
| ------------ | ---------- | ------------------------------------------------------------ |
| **pitfall**  | 踩坑与修复 | "ProTable在xxx业务域特殊场景下列宽自适应失效，需手动设置width" |
| **decision** | 方案选型   | "筛选区用QueryFilter而非antd Form"                           |
| **faq**      | 高频问答   | "POST请求接口地址必须以/开头（内部网关要求）"                |

**提炼原则：**

- 只提取真正有价值的知识，不强行填充
- 内容为标准化文本描述，便于直接消费
- 每条知识附带五维度质量评分

#### 5.1.5 质量评估与审核分级

| 评分维度      | 含义           |
| ------------- | -------------- |
| confidence    | LLM 置信度     |
| accuracy      | 与原会话一致性 |
| reusability   | 通用性         |
| completeness  | 上下文完整度   |
| actionability | 可执行性       |

**自动审核分级：**

| 条件                            | 处理方式       |
| ------------------------------- | -------------- |
| confidence ≥ 0.9 且 overall ≥ 4 | 自动入库       |
| 0.7 ≤ confidence < 0.9          | 需人工快速确认 |
| confidence < 0.7                | 需深度审核     |

#### 5.1.6 去重聚合

新知识与已有知识进行语义相似度对比：

- 相似度 > 0.85：合并为同一条，追加 evidence
- 相似度 0.5-0.85：标记关联，独立保留
- 相似度 < 0.5：作为新条目入库

### 5.2 冷启动导入：/flow-import

对于历史项目（已有大量代码但无知识库），提供冷启动导入能力：

```plain
@doc-collector → 多源资料收集
  │              （Git仓库/TAPD需求/iwiki文档/本地文档/口述录入）
  ↓
@codebase-profiler → 代码画像
  │                   （技术栈/模块/依赖/模式分析，60次搜索预算）
  ↓

```

所有导入条目初始 maturity 为 `draft`，通过后续工作流的实际使用逐步验证提升。

### 5.3 历史需求经验复用

#### 5.3.1 核心洞察

同一仓库内的需求具有连贯性——同一技术架构、组件体系、代码规范下持续迭代。同仓库内最近完成的需求就是最有价值的上下文，且需求的时间距离与代码相关性呈衰减关系：

| 时间距离 | 代码复用率         |
| -------- | ------------------ |
| 相邻需求 | ~60%               |
| 中等距离 | ~35%               |
| 较远距离 | ~15%（仅基础架构） |

#### 5.3.2 沉淀与召回

**沉淀阶段：** 需求上线后，从需求描述、对话摘要、代码变更中提取关键信息，生成摘要入库。只沉淀有价值的需求（代码变更 ≥ 50行、非纯Bug修复、有完整对话记录）。

**召回阶段：** 新需求到来时，根据需求描述和仓库信息检索相似历史需求，将匹配到的技术方案、代码变更、相关知识压缩后注入 AI 上下文。

### 5.5 开发过程自动提炼与提交：本地 → 云端完整链路

这是知识基座最核心的运转机制——**开发者无需任何额外操作，日常开发过程中产生的经验自动提炼、自动提交到云端知识库**。整个链路分为本地提取和云端入库两个阶段。

#### 5.5.1 三种触发模式

| 触发模式             | 触发时机                  | 提炼范围                   | 适用场景                   |
| -------------------- | ------------------------- | -------------------------- | -------------------------- |
| **会话级（实时）**   | 单次 AI 编码会话结束      | 本次会话的踩坑/决策        | 日常开发中的即时经验捕获   |
| **工作流级（阶段）** | /flow-run 的 ARCHIVE 阶段 | 整个工作流全生命周期的产物 | 完整需求交付后的系统性沉淀 |
| **定时批量（离线）** | 每日定时任务              | 当日所有标记"有料"的会话组 | 兜底补充，捕获遗漏的经验   |

#### 5.5.2 会话级提炼（实时触发）

开发者每次与 AI 编码助手完成一次会话后，本地插件立即执行轻量级判断：

```plain
会话结束
  │
  ├── 信号检测（关键词 + 行为模式，见 5.1.2）
  │
  ├── 无信号 → 标记"无料"，不上报，流程结束
  │
  └── 有信号 → 本地生成会话摘要包
                │
                ├── session_id, repo, branch, timestamp
                ├── 关键轮次对话摘要（报错/否定上下文）
                ├── 代码变更摘要（变更文件列表 + diff 概要）
                └── 信号类型标注
                     │
                     ▼
               上报至服务端，进入候选池
```

**设计要点：**

- 会话级提炼在本地只做"信号检测 + 摘要生成"，不做完整 LLM 提炼（节省本地算力和时间）
- 真正的知识提取由云端定时任务批量执行（见 5.5.4）
- 单次会话上报数据量控制在 2-5KB，对开发者网络和存储无感知

#### 5.5.3 工作流级提炼（ARCHIVE 阶段）

这是知识沉淀的**主路径**。当一个 `/flow-run` 工作流走完所有阶段到达 ARCHIVE 时，`@archiver` Agent 自动执行知识提取。

**ARCHIVE 阶段的输入（全流程产物）：**

```plain
工作流产物目录结构（本地临时）
└── .ai-team/output/{session-id}/
    ├── 01-product-analyse.md       ← 产品分析报告（需求背景、业务流程）
    ├── 02-tech-analyse.md          ← 技术分析报告（技术栈、依赖、风险点）
    ├── 03-architecture.md          ← 架构设计（方案选型、决策理由）
    ├── 04-implementation-log.md    ← 实现记录（代码变更清单、关键实现路径）
    ├── 05-build-verify.md          ← 构建验证报告（踩坑记录、修复方案）
    └── manifest.yaml               ← 工作流元信息（仓库、分支、耗时、阶段状态）
```

**@archiver Agent 的提炼步骤：**

```plain
Step 1: 遍历产物目录，识别可提取的知识信号
        ├── 01/02 中是否有 model / process 描述？
        ├── 03 中是否有 decision（选型 + 理由）？
        ├── 04 中是否有实现过程中的坑和解决方案？
        └── 05 中是否有验证阶段的报错和修复？

Step 2: 对每个信号调用 LLM 提取结构化知识条目
        输入：信号所在上下文 + 前后文（≤2000 tokens/条）
        输出：知识条目 JSON（type, title, content, tags）

Step 3: 本地预去重
        检查本次提取的条目之间是否有重复
        相似度 > 0.9 的合并为一条

Step 4: 生成 knowledge-references（引用记录）
        记录本次工作流各阶段引用了哪些已有知识
        用于更新云端知识的 evidence.last_referenced

Step 5: 组装提交包，通过 MCP ingest-knowledge 推送至云端
```

**提取的知识条目格式（本地生成，提交云端）：**

```json
{
  "extraction_id": "ext-20260415-a3f8c2",
  "session_id": "flow-20260415-001",
  "repo": "git@internal:team/project.git",
  "branch": "feature/ad-campaign-list",
  "entries": [
    {
      "type": "pitfall",
      "title": "ProTable 在广告列表页列宽自适应失效",
      "content": "在广告管理列表页中使用 ProTable 时，当 columns 中配置了 ellipsis: true，且未显式设置 width 属性，列宽自适应会失效，导致列宽塌缩为 0。需在每个 column 中显式设置 width 值。",
      "tags": ["ProTable", "列宽", "广告列表"],
      "source_phase": "05-build-verify",
      "source_evidence": "见 build-verify.md 第3轮调试记录"
    },
    {
      "type": "decision",
      "title": "广告列表筛选区采用 QueryFilter 而非 antd Form",
      "content": "选择 QueryFilter 的原因：(1) 与团队现有中后台模版一致；(2) 内置了查询/重置/展开逻辑，减少重复代码；(3) 支持远程搜索，满足广告主名称模糊搜索需求。",
      "tags": ["QueryFilter", "筛选区", "组件选型"],
      "source_phase": "03-architecture",
      "source_evidence": "见 architecture.md 组件选型决策"
    }
  ],
  "knowledge_references": [
    { "id": "TK-SB-003", "used_in_phase": "04-implementation" }
  ]
}
```

#### 5.5.4 云端接收与处理流水线

本地通过 MCP ingest-knowledge 提交后，云端执行完整的处理流水线：

```plain
                    本地提交（MCP ingest-knowledge）
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    ☁️ 云端处理流水线                            │
│                                                             │
│  Step 1: 接收验证                                            │
│    · 校验 repo / branch 归属和权限                            │
│    · 校验条目格式完整性                                        │
│    · 写入 contributions/pending/ 暂存                         │
│                                                             │
│  Step 2: 去重聚合                                            │
│    · 新条目 ↔ 已有知识库 语义相似度计算                          │
│    · 相似度 > 0.85 → 合并，追加 evidence                       │
│    · 相似度 0.5-0.85 → 标记关联，独立保留                       │
│    · 相似度 < 0.5 → 作为新条目候选                              │
│                                                             │
│  Step 3: 质量评估                                            │
│    · 对每条（新条目 + 已合并条目）执行五维度评分                    │
│    · confidence / accuracy / reusability / completeness      │
│      / actionability                                        │
│                                                             │
│  Step 4: 自动审核路由                                         │
│    · overall ≥ 4 且 confidence ≥ 0.9 → 自动入库（~89%）       │
│    · 0.7 ≤ confidence < 0.9 → 入审核队列（快速确认）            │
│    · confidence < 0.7 → 入深度审核队列                         │
│                                                             │
│  Step 5: 入库 + 成熟度初始化                                   │
│    · 自动入库条目：maturity = draft                            │
│    · 更新 evidence.contributors[] 和 evidence.created_at      │
│    · 写入对应 Layer（项目级 → Layer 3）                        │
│                                                             │
│  Step 6: 知识提升判定（异步）                                   │
│    · 如果是工作流级提交 → 检查本次提取的条目是否满足提升条件       │
│    · Q1: 是否项目特有？→ 是：留在 Layer 3                       │
│    · Q2: 是否通用技术？→ 是：提升到 Layer 1 (tech-wiki)         │
│    · Q3: 是否通用业务？→ 是：提升到 Layer 2 (biz-wiki)          │
│                                                             │
│  Step 7: 更新索引 + log.md                                    │
│    · 重建对应 catalog.md                                     │
│    · 追加 log.md 操作记录                                     │
│    · 知识点在下次 MCP search 时立即可检索                       │
└─────────────────────────────────────────────────────────────┘
```

#### 5.5.5 定时批量提炼（离线兜底）

对于会话级上报但未在工作流中被处理的候选池数据，云端定时任务每日执行批量提炼：

```plain
每日 02:00 UTC 触发
  │
  ├── 1. 聚合当日所有"有料"会话（按 repo + branch 分组）
  │
  ├── 2. 筛选满足条件的会话组（session_count > 1 或 rounds > 10）
  │
  ├── 3. 调用 LLM Pipeline 批量提取知识条目
  │     （输入：会话组上下文，输出：结构化条目列表）
  │
  ├── 4. 执行去重聚合 → 质量评估 → 自动审核 → 入库
  │      （与 5.5.4 的 Step 2-7 流程一致）
  │
  └── 5. 生成每日沉淀报告
        （新增条目数、按 type 分布、平均置信度）
```

**设计要点：**

- 定时任务是对工作流级提炼的兜底补充，捕获那些"还没走完整工作流但有价值"的经验
- 离线提炼的条目初始 maturity 同样为 draft，后续工作流引用时自动验证提升
- 已通过工作流 ARCHIVE 提交过的会话不会重复提炼

#### 5.5.7 对开发者完全透明

整个提炼 + 提交过程对开发者零感知、零打断：

| 开发者感知           | 说明                                                         |
| -------------------- | ------------------------------------------------------------ |
| 是否需要手动操作？   | **不需要**。会话级自动检测上报，工作流级 ARCHIVE 自动执行    |
| 是否打断编码？       | **不打断**。会话级摘要生成 < 100ms，工作流级在后台异步运行   |
| 是否消耗本地算力？   | **极小**。会话级只做轻量信号检测，LLM 提炼全部在云端执行     |
| 是否占用网络带宽？   | **极小**。单次上报 2-5KB，工作流提交包 < 50KB                |
| 如何知道沉淀了什么？ | ARCHIVE 完成后终端输出摘要："本次沉淀 2 条 pitfall，1 条 decision" |
| 沉淀错了怎么办？     | 可在管理后台查看并修正；云端 Lint 定期检测矛盾；衰减机制自动淘汰 |

## 六、知识消费能力

### 6.1 设计理念：本地零存储，云端按需取

**核心原则：本地不拉取、不存储任何知识经验文档。** 开发者本地环境只部署一个轻量级"知识网关"文档（`knowledge-gateway.md`，约 200 行），它不包含任何实际知识内容，只告诉 LLM **如何调用云端知识库**。

```plain
┌────────────────────────────────────────────────────────────┐
│               本地 vs 云端 职责边界                           │
├────────────────────────────┬───────────────────────────────┤
│   💻 本地（仅一个文件）      │   ☁️ 云端（所有知识存储）       │
├────────────────────────────┼───────────────────────────────┤
│ · knowledge-gateway.md     │ · 五层存储架构（全部知识条目）   │
│ · 工作流引擎                │ · MCP Server（search/ingest）  │
│ · AI 编码插件               │ · 三级索引（全景/分类/完整条目） │
│                            │ · 向量检索 / 关键词检索        │
│                            │ · 成熟度管理 / 衰减 / Lint     │
└────────────────────────────┴───────────────────────────────┘
```

### 6.2 知识网关文档（knowledge-gateway.md）

这是本地环境中的**唯一知识相关文档**，约 200 行，内容结构如下：

```markdown
# 知识基座网关

## MCP Server 信息
- 地址：http://knowledge-mcp.internal/api
- 认证方式：内网自动认证

## 可用工具

### search-knowledge
- 用途：按关键词或语义检索团队知识库
- 参数：query（必填）、scope（repo/domain/global）、limit（默认5）
- 返回：匹配知识条目的标题、摘要、完整内容、相似度分数

### search-history-requirements
- 用途：检索同仓库历史需求经验
- 参数：repo_path（必填）、description（必填）

## 查询策略
1. 遇到报错 → 优先用错误信息作为 query 调用 search-knowledge
2. 技术选型前 → 查询是否有相关 decision 或 guideline
3. 实现具体功能前 → 查询同仓库历史需求经验
4. 代码审查时 → 查询相关 pitfall 和 anti-pattern

## 知识分类速览
- pitfall：踩坑经验（最多，约50%）
- faq：高频问答（约30%）
- decision：方案选型（约20%）
```

**网关文档的定位**：它是一份"使用说明书"而非"知识内容"。LLM 在需要知识支持时，先读这份网关了解如何调用，然后通过 MCP 工具精准获取云端知识。本地始终只有这一个文档，上下文消耗约 200 行。

### 6.3 云端三级渐进式索引

虽然索引结构在云端，但 LLM 通过 MCP 查询时，云端内部仍采用三级渐进式索引来保证检索效率：

| 层级                  | 作用                              | 检索时消耗                 |
| --------------------- | --------------------------------- | -------------------------- |
| **Layer A: 全景目录** | 全局索引，快速定位相关分类        | 内部使用，不返回客户端     |
| **Layer B: 分类清单** | 按 type/domain 过滤，逐条摘要匹配 | 内部使用，不返回客户端     |
| **Layer C: 完整条目** | 精准命中后返回给客户端            | 仅返回匹配条目（精简摘要） |

**检索流程（LLM 视角）**：

```plain
Step 1: LLM 读本地 gateway.md → 了解 MCP 工具和查询策略
Step 2: LLM 调用 MCP search-knowledge(query="具体问题描述")
Step 3: 云端内部按全景目录 → 分类清单 → 完整条目 逐级匹配
Step 4: 云端返回精准匹配结果（非全量文档，仅摘要+关键内容）
Step 5: LLM 基于返回结果生成答案
```

**与"本地存储全量知识"对比**：

| 维度           | 本地存储方案                 | 云端按需检索方案                 |
| -------------- | ---------------------------- | -------------------------------- |
| 本地文档数     | 几十到上百个 .md 文件        | **1 个** gateway.md              |
| 本地上下文消耗 | Git clone 后可能数千行       | **~****200 行**                  |
| 知识时效性     | 依赖 git pull 同步，可能滞后 | **实时**，查询即最新             |
| 存储空间       | 随知识增长线性膨胀           | **恒定** ~200行                  |
| 知识安全       | 完整知识分布在每台开发机     | **云端集中管控**，无泄漏风险     |
| 切换业务域     | 需切换 git 仓库或分支        | **零成本**，MCP 自动按 repo 匹配 |

### 6.4 查询预算机制

每个工作流阶段的 Agent 有独立的查询预算，聚焦不同类型的知识：

| 阶段            | 查询焦点                      | 重点知识类型                        | 预算 |
| --------------- | ----------------------------- | ----------------------------------- | ---- |
| ANALYSE_PRODUCT | 业务知识 (Layer 2) + 历史需求 | model, process, pitfall             | 3条  |
| ANALYSE_TECH    | 技术知识 (Layer 1) + 归档索引 | decision, guideline(avoid), pitfall | 5条  |
| ARCHITECT       | 架构模式 + 实体关系           | decision, model                     | 3条  |
| IMPLEMENT       | 编码实践 + 团队约定           | guideline, pitfall                  | 5条  |
| BUILD_VERIFY    | 反模式库                      | pitfall, guideline(avoid)           | 3条  |

### 6.5 分级召回策略

```plain
第一优先级：当前仓库知识 (scope = repo)
  → 最相关，与当前项目直接相关
  → 找到 ≥3条（相似度>0.8）则直接返回

第二优先级：业务域级知识 (scope = domain)
  → 同 Git 组织下的通用知识
  → 合并结果，仓库级排前面

第三优先级：全局知识
  → 无仓库限制的通用知识
  → 仍不足时放宽过滤条件
```

### 6.6 知识引用追踪闭环

Agent 查询知识后，在输出产物中记录引用：

```json
{
  "knowledgeReferences": [
    { "id": "TK-SB-003", "title": "分页查询延迟关联优化", "usedIn": "复用评级 Step 2" },
    { "id": "BK-AD-G004", "title": "广告预算扣减并发控制规则", "usedIn": "业务规则参考" }
  ]
}
```

ARCHIVE 阶段会读取所有阶段产物中的 `knowledgeReferences`，批量更新 `evidence.last_referenced` 字段，形成**自动化的引用追踪闭环**——被引用的知识 maturity 会自动提升，长期未引用的会自动衰减。

## 七、云端统一配置下发

### 7.1 设计目标

| 指标         | 传统方式（本地配置）             | 云端统一下发              |
| ------------ | -------------------------------- | ------------------------- |
| 初次配置耗时 | ~30分钟（手动创建文件、配置MCP） | 0分钟（打开项目自动拉取） |
| 规则变更同步 | 逐一通知、手动更新               | 云端修改后自动同步        |
| 业务域切换   | 手动切换配置                     | 自动识别仓库归属          |
| 团队一致性   | 难以保证                         | 统一下发                  |

### 7.2 配置匹配优先级（四层）

```plain
1. 业务域配置（显式指定）         ← 最高优先级
2. 仓库规则匹配（Git Group/Repo 静态匹配）
3. 人群配置（按工号圈选）
4. 全局默认配置                   ← 最低优先级
```

### 7.3 配置内容范围

**重要区分：配置下发的是"元数据/行为规则"，知识内容始终存储在云端通过 MCP 按需获取。**

| 配置类型             | 内容                                    | 加载策略                 | 存储位置                             |
| -------------------- | --------------------------------------- | ------------------------ | ------------------------------------ |
| agent.md             | Agent 行为定义、团队规范                | 打开仓库自动加载         | 本地（~100行）                       |
| knowledge-gateway.md | MCP Server 信息、查询策略、知识分类速览 | 打开仓库自动加载         | **本地唯一知识入口**（~200行）       |
| mcp.json             | MCP Server 配置                         | 打开仓库自动加载         | 本地                                 |
| domain.yaml          | 业务域规则、技术栈约束                  | 打开仓库自动加载         | 本地（~50行）                        |
| skills/              | 技能包（工作流、prompt模板）            | 打开仓库自动加载         | 本地                                 |
| **个人偏好**         | 编码风格、个人 prompt 模板、语言偏好    | **用户级**，跟人不跟项目 | **本地** `~/.ai-team/`（可选云同步） |
| **所有知识内容**     | 踩坑经验、FAQ、决策、技术方案等         | **MCP 按需检索**         | **☁️** **云端**                       |
| **三级索引**         | 全景目录、分类清单、完整条目            | **MCP 按需检索**         | **☁️** **云端**                       |

**本地文档总量控制**：开发者本地每个项目下由配置中心自动写入的项目级文件总行数控制在 500 行以内（agent.md + knowledge-gateway.md + domain.yaml + mcp.json），不随知识库规模增长而膨胀。个人偏好（`~/.ai-team/`）存储在用户目录，属于用户级而非项目级，不计入项目文件总量。

### 7.4 业务域隔离

不同业务域的知识在**云端物理隔离**，确保 AI 始终使用与当前项目匹配的知识。本地网关文档通过 MCP 调用时自动携带仓库信息，云端按仓库归属匹配对应业务域的知识：

```plain
☁️ 云端 team-knowledge/
├── domain-common/          ← 通用知识（所有域共享）
├── domain-supply-chain/    ← 供应链业务域知识
├── domain-ads/             ← 广告业务域知识
└── domain-merchant/        ← 商家业务域知识

💻 本地（每个项目仅一份网关）
└── knowledge-gateway.md   ← 内容按仓库归属动态生成
                              MCP 调用时自动携带 repo 信息
                              云端据此匹配对应业务域知识
```

每个业务域在云端独立配置和存储：agent.md、mcp.json、domain.yaml、skills/ 等元数据按业务域生成后下发到本地；知识内容在云端按业务域隔离存储，通过 MCP 按域检索。

## 八、团队协作与治理

### 8.1 独立 Git 仓库架构

团队知识库为独立 Git 仓库，部署于**服务端（Git Server）**，不寄生于任何业务项目，**开发者本地不克隆该仓库**。

```plain
☁️ 服务端 team-knowledge.git                 ← 独立 Git 仓库（仅服务端）
├── knowledge-catalog.md              ← 全景目录（MCP 内部使用）
├── .knowledge-config.yaml            ← 团队配置（成员、冲突策略）
├── team-conventions/                 ← Layer 0-T: 团队约定
│   ├── coding-standards.md
│   └── commit-conventions.md
├── tech-wiki/                        ← Layer 1: 技术知识
│   ├── catalog.md
│   ├── patterns/
│   └── anti-patterns/
├── biz-wiki/{domain}/                ← Layer 2: 业务知识
│   ├── catalog.md
│   ├── entities/
│   └── pitfalls/
├── project-profiles/                 ← 项目画像
└── contributions/                    ← 贡献暂存区
    ├── pending/
    └── conflicts/

注意：Layer 0-P 个人偏好不在本仓库中。它存储在开发者本地 `~/.ai-team/` 目录。
```

**独立仓库的三重价值：**

1. **跨项目共享**：多个项目通过 MCP 连接同一知识仓库，知识自动复用
2. **生命周期独立**：业务项目归档，知识不丢失
3. **权限独立**：知识库贡献和消费权限独立管理
4. **本地零负担**：开发者无需 clone，知识消费通过 MCP 按需获取，知识贡献通过工作流 ARCHIVE 阶段自动推送

### 8.2 贡献模式："贡献暂存 + 异步合并"

借鉴区块链核心思想，用 Git 作为实现载体：

| 区块链思想         | 知识基座实现            | 机制                                                  |
| ------------------ | ----------------------- | ----------------------------------------------------- |
| 不可篡改的追加日志 | log.md 只追加不修改     | 每条变更记录贡献者、时间、会话哈希                    |
| 贡献可溯源         | evidence.contributors[] | 类似 Git blame，粒度为知识条目级                      |
| 共识机制           | maturity 多人验证提升   | draft→verified: 1人验证; verified→proven: ≥2人+≥2项目 |

**log.md 示例：**

```plain
## [2026-04-09] ingest | [Steven] | 门店履约视图归档 | +1 decision, +2 guideline | #a3f8c2
- 新增 DEC-005: 地图组件选型（腾讯地图 GL JS SDK）
- 新增 GL-012: fitBounds 在 flexbox 布局中的替代方案 (polarity=recommend)

## [2026-04-12] verify | [Alice] | 跨项目验证 | maturity↑ 2 | #c5f0e2
- TK-SB-003 "分页查询延迟关联优化" (verified→proven, 2 projects)
```

### 8.3 冲突解决策略

| 冲突类型               | 处理方式                                        |
| ---------------------- | ----------------------------------------------- |
| 纯新增（不同条目）     | 自动合并，两条都保留                            |
| 证据追加（同条目验证） | 自动合并，evidence 数组合并去重                 |
| 成熟度提升             | 自动合并                                        |
| 内容矛盾               | 写入 `contributions/conflicts/`，通知管理员裁决 |
| 成熟度冲突（一升一降） | 保留较低成熟度 + 标记 contradiction             |

**设计理念**：多数情况自动处理，只有真正的内容矛盾才需人工介入，让知识共建尽可能低摩擦。

### 8.4 Lint 质量治理

知识库不能只进不出，需定期 Lint：

| 检查项                        | 处理方式                 |
| ----------------------------- | ------------------------ |
| 索引不一致                    | 自动修复                 |
| 孤儿条目（无引用、无验证）    | 降级为 draft             |
| 矛盾检测（同主题相反结论）    | 标记冲突，等待管理员裁决 |
| 过时检测（6月未引用的 draft） | 自动归档                 |
| 重复/相似条目                 | 标记合并候选             |
| 成熟度衰减                    | 按规则自动降级           |

**Lint 触发方式：**

- 自动：每完成 10 个工作流自动触发
- 手动：`/knowledge lint` 命令
- 提醒：连续 30 天未执行时在下次 `/flow-run` 启动时提醒

## 九、人机交互突破

### 9.1 问题：工作流的"在场依赖"

传统 Agent 工作流的隐含假设——**操作者坐在电脑前，IDE 打开着，随时响应 Agent 请求**——与实际工作日结构严重不匹配：

```plain
一个典型工作日中，真正"坐在工位操控 Agent"的时间可能不到 4 小时。
工作流在"等人确认"时暂停，交付效率至少折半。
```

### 9.2 解决方案：远程操控 + 跨设备接管

| 能力           | 说明                                  | 对工作流的意义           |
| -------------- | ------------------------------------- | ------------------------ |
| 跨设备会话接管 | 手机/平板/电脑均可接管同一 Agent 会话 | 工作流不因设备切换而中断 |
| 24小时待机     | 开发机上的 Agent 持续运行             | 工作流可 7×24 小时流转   |
| 异步审批       | 人工确认节点异步模式                  | 碎片时间推进工作流       |
| 状态持久化     | 文件系统即状态机                      | 断点恢复，不丢进度       |
| 通知触达       | 关键节点企业微信主动推送              | 不错过关键决策点         |

### 9.3 架构设计启示

**好的 Harness 工程不仅要设计"Agent 怎么跑"，还要设计"人怎么随时参与"。**

- **状态持久化**：工作流状态以文件形式持久化，非内存
- **断点恢复**：每个阶段出入口有明确持久化产物
- **异步审批**：Agent 提交产物后暂停等待，人类可在任意时间、任意设备审批
- **通知触达**：关键节点通过企业微信主动推送

## 十、指标体系

### 10.1 分阶段建设策略

**先有量，再优化准。** 知识消费者是 AI 而非人——AI 能从海量信息中快速筛选最相关内容，我们只需通过评测验证召回有效率即可。

### 10.2 V1 指标（覆盖面）

| **知识总量**     | 活跃知识条目数     | 持续增长 |
| **知识引用频次** | 单条知识被引用次数 | 持续增长 |

| **问题解决率** | 知识帮助解决问题的比例     | 用户反馈 |
| **知识有用率** | 单条知识的正向反馈占比     | 用户反馈 |

### 10.4 辅助分析指标

| 指标            | 用途             |
| --------------- | ---------------- |
| 热门查询词      | 发现用户关注领域 |
| 零结果查询词    | 发现知识库缺口   |

### 11.2 四条数据通道

| 通道     | 方向                | 内容                                                 | 传输量                    |
| -------- | ------------------- | ---------------------------------------------------- | ------------------------- |
| 配置下发 | 配置中心 → Client   | agent.md, gateway.md, mcp.json, domain.yaml, skills/ | ~500行/次                 |
| 知识消费 | Client → MCP Server | 查询请求 → 精准结果（非完整文档）                    | 查询~50字，返回~200-500字 |
| 数据上报 | Client → 服务端     | 会话记录、代码变更、埋点统计                         | 会话级                    |
| 知识写入 | 工作流 → MCP Server | 知识条目、成熟度更新、引用记录                       | 条目级                    |

### 11.3 关键技术决策

| 决策点            | 选择                               | 理由                                            |
| ----------------- | ---------------------------------- | ----------------------------------------------- |
| **知识存储位置**  | ☁️ 云端（Git 仓库）                 | 集中管控、跨项目共享、开发者本地零负担          |
| **个人偏好存储**  | 💻 本地为主 + ☁️ 可选云同步          | 隐私安全 + 离线可用 + 跨设备便利（见 4.1.1）    |
| **个人→团队边界** | 永不自动提升，仅"分享到团队"单向桥 | 物理隔离，团队知识不受个人偏好污染              |
| **本地知识入口**  | 单一 gateway.md                    | 仅 ~200 行，告诉 LLM 如何调用云端，不存实际知识 |
| 存储格式          | Markdown 文件                      | 人类可读、Git 版本化、IDE 原生                  |
| 消费协议          | MCP（Model Context Protocol）      | 标准协议、按需调用、不传输完整文档              |
| 状态管理          | 文件系统即状态机                   | 无数据库依赖、支持断点恢复                      |
| 检索演进          | 关键词 → 向量检索                  | 关键词满足 < 1000 条场景，向量支持语义发现      |
| 配置匹配          | 四级优先级                         | 仓库维度优先，兼顾灵活性和一致性                |
| 同步机制          | **不 git clone，不文件同步**       | 知识消费全部走 MCP 实时查询，无同步滞后问题     |

## 十二、实施路径

### 12.1 分阶段落地计划

**Phase 1：基础建设（Month 1-2）**

- 搭建云端独立 Git 知识仓库骨架
- 实现五层存储目录结构
- 完成知识条目标准模板和元数据定义
- 实现云端三级渐进式索引和 MCP search-knowledge 接口
- 实现 knowledge-gateway.md 按仓库动态生成和下发
- 建立成熟度模型和自动衰减规则

**Phase 2：智能沉淀（Month 2-3）**

- 实现会话信号识别和上报机制
- 开发 LLM 知识提炼 Pipeline
- 实现去重聚合和质量评估
- 建立审核后台（含原始会话查看）
- 冷启动导入（/flow-import）能力

**Phase 3：云端配置（Month 3-4）**

- 实现四级优先级配置匹配
- 开发配置下发通道（增量更新）
- 实现业务域自动识别和隔离
- Skills 统一管理和下发
- MCP Server 开发和部署

**Phase 4：消费闭环（Month 4-5）**

- 知识按需检索（关键词检索）
- 查询预算控制和引用追踪
- 工作流各阶段知识注入
- 历史需求经验复用
- 指标体系搭建和可视化

**Phase 5：进阶优化（Month 5-6）**

- 向量检索迁移（Embedding + LanceDB）
- 冲突解决自动化和 Lint 治理
- 知识自动提升和衰减全自动化
- 远程操控和跨设备接管
- 全异步人机协作模式

### 12.2 风险与应对

| 风险                     | 影响               | 应对策略                                    |
| ------------------------ | ------------------ | ------------------------------------------- |
| AI 提炼知识质量低        | 知识库充斥噪音     | 五维质量评分 + 分级审核 + 衰减自动清理      |
| 知识库膨胀失控           | 检索效率下降       | Lint 自动归档 + 过时检测 + 预算控制         |
| 团队贡献意愿低           | 知识库成为"一人库" | 自动沉淀（零额外成本）+ 贡献可视 + 引用追踪 |
| 跨业务域知识污染         | AI 给出错误建议    | 物理隔离 + 四级优先级 + 源头过滤            |
| 模型能力跃迁导致方案过时 | 架构投资浪费       | 知识层独立于工具链 + Markdown 可迁移        |

## 十三、附录

### 13.1 术语表

| 术语                    | 定义                                                         |
| ----------------------- | ------------------------------------------------------------ |
| **Harness Engineering** | 引导和约束 AI 模型能力的工程实践，强调上下文管理、架构约束和持续治理 |
| **知识基座**            | 服务于 AI 编码场景的团队知识工程基础设施                     |
| **云-端分离**           | 所有知识内容存储在云端，本地仅部署一个轻量网关文档，通过 MCP 协议按需获取 |
| **知识网关文档**        | 本地唯一知识入口（knowledge-gateway.md，~200行），告诉 LLM 如何调用云端知识库，不存储实际知识 |
| **知识沉淀**            | 将隐性经验转化为结构化、可检索的知识条目的过程               |
| **信号驱动**            | 通过识别会话中的报错、否定、多轮调试等信号来捕获"踩坑现场"   |
| **成熟度**              | 知识经过验证的程度：draft → verified → proven                |
| **渐进式索引**          | 云端内部的三级索引结构，让检索高效精准，索引文件不传输到本地 |
| **查询预算**            | 限制 Agent 每个阶段可查询的知识条数，防止上下文膨胀          |
| **MCP Server**          | 提供知识检索和写入能力的标准协议服务，部署于云端             |
