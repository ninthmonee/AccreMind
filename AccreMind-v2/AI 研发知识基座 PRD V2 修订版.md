## 一、产品定位与价值

### 1.1 产品定位

AI 研发知识基座是服务于 AI 辅助编程的团队知识基础设施。它将团队规范、业务模型、架构决策和有证据支持的实践经验转化为可授权检索、可验证、可纠错的知识，供开发者及其 AI 编码助手在适用场景中使用。

核心价值是：开发者 A 解决过的问题，开发者 B 可以复用其经验，减少重复排查与返工。系统追求团队知识的持续有效积累，不将知识数量增长视为价值实现。

### 1.2 目标问题

| 问题 | 典型表现 | 目标结果 |
| --- | --- | --- |
| 经验分散 | 有效经验散落在会话、个人记录和历史需求中 | 有来源的经验进入团队可检索空间 |
| 重复排查 | 相同业务约束或故障被多次发现 | 在正确条件下复用已验证结论 |
| 上下文缺失 | AI 不知道内部术语、版本约束或例外 | 返回知识时同时提供适用条件和证据 |
| 配置不一致 | 成员连接方式、规则版本不一致 | 首次接入后按授权项目获取受控配置 |
| 错误持续传播 | 过时或错误经验被重复引用 | 能反馈、暂停使用、撤回和替代 |

不预设所有 AI 编码工具具有相同限制。试点需先记录现有工具和工作流已经解决的问题，避免重复建设。

### 1.3 设计原则

1. 知识独立于具体编码工具，客户端通过适配层接入。
2. 准确性、适用性和覆盖面从首版共同评估。
3. 自动化负责发现候选和整理证据，发布和验证按明确规则执行。
4. 引用不等于验证，使用频率不等于正确性。
5. 团队知识以云端为权威源，本地不复制全量知识库；允许必要的配置、短期结果和可靠提交队列。
6. 个人内容与团队内容隔离，共享范围扩大需要授权审核。
7. 知识返回给 Agent 后作为资料使用，不自动获得执行指令权限。
8. 所有发布内容可定位版本、来源、维护人，并支持撤回。
9. 优先沉淀有证据支持的知识增量：原因、取舍、例外、外部约束、失败路径和变更顺序；可直接恢复的代码事实优先索引，已有权威内容优先链接。

### 1.4 核心目标：保存代码之外的必要上下文

每个候选必须回答：**“下次只给 AI 当前代码与已授权权威文档，它会缺少什么信息，可能因此做错什么或重复排查什么？”**

“难以发现”是相对于指定仓库版本、可访问资料和查阅预算的判定，不是关于所有 AI 能力的永久结论。单次检索失败、模型猜错或达到预算上限，均不能证明知识在代码中不存在。代码中的历史注释、测试、ADR 和版本记录也可能已经包含所需依据。

本产品区分两类价值：一是补充当前资料无法充分表达的结论依据；二是降低已存在资料的发现成本。前者生成有证据的经验条目，后者优先建设导航和授权检索入口。团队强制规范可以保留受控镜像用于执行，但须指向唯一权威来源，并标记为规范镜像，不计入新增经验。

不设置每次会话、每个需求必须产出知识的配额。零条新增知识可以是正确结果。

## 二、用户、角色与权限

### 2.1 用户角色

- 一线开发者：检索知识、提交候选、反馈错误、提交应用和验证证据。
- 新人或跨域开发者：通过术语、约束及历史经验理解授权项目。
- 领域负责人／TL：审核本领域内容、判断适用性、确认验证证据。
- 知识管理员：管理分类、维护队列、协调冲突、执行授权范围内的治理。
- 平台管理员：管理身份集成、服务配置、运行和安全策略；该角色不自动获得全部知识正文权限。

### 2.2 权限矩阵

所有权限均限制在角色被授予的团队、业务域和仓库范围内。

| 操作 | 开发者 | 领域负责人／TL | 知识管理员 | 平台管理员 |
| --- | --- | --- | --- | --- |
| 检索已发布知识 | 按内容授权 | 按内容授权 | 按内容授权 | 按内容授权 |
| 提交候选／编辑建议／错误反馈 | 可以 | 可以 | 可以 | 按内容授权 |
| 修改已发布正文 | 提交修订候选 | 审核后发布新版本 | 按内容授权审核 | 不默认授予 |
| 发布／撤回知识 | 不可以 | 本领域可以 | 按内容授权可以 | 不默认授予 |
| 批准成熟度变化 | 不可以 | 审核验证证据 | 按内容授权审核 | 不默认授予 |
| 裁决内容冲突 | 提供证据 | 判断专业结论 | 协调并记录决议 | 不默认授予 |
| 批准共享范围扩大 | 提出申请 | 源内容负责人确认 | 校验目标范围授权 | 不默认授予 |
| 管理系统与身份接入 | 不可以 | 不可以 | 不默认授予 | 可以 |

候选贡献者不能单独批准自己提交的候选或验证记录。试点需配置至少一名有权审核的其他成员。管理员不能以系统管理权限绕过内容授权。

## 三、产品范围与用户旅程

### 3.1 MVP 范围

首版面向一个试点团队、一个业务域及其中少量明确授权仓库，先适配一个实际使用的 AI 编码入口。

必须交付：

1. 已有文档人工导入与结构化候选生成。
2. 统一知识模型、来源追踪、版本及适用条件。
3. 身份认证、服务端范围授权和关键词检索。
4. 候选审核、发布、修订、撤回和冲突处理。
5. 从显式触发的会话片段或交付产物生成候选。
6. 检索、引用、应用、验证分离的事件记录。
7. 基础客户端接入、重试、故障降级和可观测性。
8. 离线检索评测与实际任务效果评估。
9. 每个候选的代码可发现性与新增信息判定、证据绑定、明确分流和审核展示（见 §4.5、§6.8），属于 MVP 必需能力。

### 3.2 后续范围

| 能力 | 建设前提 |
| --- | --- |
| 自动会话信号采集与离线提炼 | 首个客户端事件接口、采集边界和质量评测通过 |
| 多客户端适配、多来源连接 | MVP 证明复用收益，且各来源权限可映射 |
| 向量或混合检索 | 评测表明关键词方案存在明确缺口 |
| 低风险候选自动发布 | 人工审核样本能支持自动发布的可靠性判断 |
| 自动成熟度提升 | 验证规则可机器判定且完成独立校验 |
| 个人偏好云同步 | 独立的个人数据协议和同步需求得到确认 |
| Skills 集中分发 | 配置审批、签名验证和回滚能力就绪 |
| 跨设备会话接管与异步审批 | 作为工作流平台单独立项并定义安全与恢复能力 |

完整 16 阶段工作流不是 MVP 前置依赖。保留 ARCHIVE 等集成接口，但已有开发流程可以独立使用知识服务。

### 3.3 核心用户故事

**经验复用**：A 在某依赖版本和布局条件下解决故障，提交带证据的候选。负责人确认后发布。B 在相同条件下检索到条目，看到适用范围与验证程度，应用后记录针对该故障的验证结果。

**错误纠正**：B 发现建议在另一版本下不适用，提交反馈。条目进入待复核或被暂停检索，负责人判断是补充适用条件、拆分版本，还是撤回并发布替代条目。已知引用者能收到站内更正提示。

**新人理解业务**：新人检索术语时，获得有权访问的领域模型与当前规则，能沿来源链接了解依据。无权限来源的片段和标题均不显示。

### 3.4 验收场景

| 场景 | 预期行为 |
| --- | --- |
| 匹配到适用知识 | 返回稳定 ID、版本、适用条件、关键内容和来源 |
| 只找到不适用版本 | 不当作直接建议；可返回有明确标记的相关资料 |
| 没有可靠知识 | 返回零结果及原因类别，不填充无关条目 |
| 用户篡改 repo/domain 参数 | 服务端拒绝越权，不泄漏目标内容是否存在 |
| 重复提交同一候选 | 返回原提交结果，不重复生成条目或证据 |
| 发布后被撤回 | 后续检索立即经过状态过滤，不再返回其正文 |
| 服务不可用 | 明确知识查询失败；普通编码流程可继续，不能声称完成知识校验 |
| 候选未经审核 | 普通检索不可见，仅在有权限的审核界面可见 |

## 四、知识组织与数据模型

### 4.1 共享层次

保留五层组织方式，但不将目录层次等同于权限体系。

| 层 | 内容 | 存储与共享 | 生命周期 |
| --- | --- | --- | --- |
| Layer 0-P | 个人偏好与个人草稿 | 本地个人空间；MVP 不提供云同步 | 由个人管理 |
| Layer 0-T | 团队约定 | 云端，团队内授权共享 | 持续复核 |
| Layer 1 | 通用技术知识 | 云端，授权团队或项目使用 | 随技术版本变化 |
| Layer 2 | 业务领域知识 | 云端，业务域授权 | 随业务演进 |
| Layer 3 | 项目知识 | 云端，项目授权 | 随项目与版本变化 |

个人空间不参加自动团队采集；只有显式“分享到团队”才生成候选。团队会话采集也需排除个人文件内容与偏好指令，不能以会话上报绕过个人空间边界。

Layer 3 到 Layer 1/2 的变化称为“共享范围变更”，不称为成熟度提升。系统可以建议抽象通用结论，但必须经源内容负责人批准、移除不能扩散的信息，并校验目标范围。派生条目保留来源关系；原证据的可见范围不自动扩大。

### 4.2 知识类型

统一使用五种主类型，每条只有一个主类型；标签和关系表达交叉属性，不宣称内容天然完全互斥。

| type | 含义 |
| --- | --- |
| model | 实体、结构和关系 |
| decision | 选型结论、背景及取舍 |
| guideline | 推荐或禁止做法，通过 polarity 区分 recommend/avoid |
| pitfall | 故障条件、现象、原因和解决方法 |
| process | 流程、状态机和操作步骤 |

FAQ 是问答展示形式，使用 `presentation: faq`，不作为第六种类型。历史需求使用独立的 RequirementSummary 对象，通过知识 ID 关联，不混入主类型枚举。

### 4.3 核心对象

| 对象 | 必需信息 |
| --- | --- |
| KnowledgeEntry | id、revision、type、title、claim、context、scope、owner、状态、来源、时间，以及 §4.5 的 knowledge_role、rationale、invalidation_triggers、capture_assessment_id |
| Evidence | id、source_type、source_ref、source_revision、定位、访问范围、证据摘要 |
| ValidationRecord | 知识 ID/版本、任务、环境、验证方法、预期/实际结果、判定、提交及审核人 |
| Contribution | contribution_id、幂等键、贡献者、来源事件、候选内容、处理状态、capture_assessment_id |
| CaptureAssessment | question、资料检查范围、可发现性结果、知识增量及证据、缺失代价、优先级、分流和审核结论（§4.5） |
| UsageEvent | event_id、事件类型、任务、知识 ID/版本、时间、结果或反馈 |
| RequirementSummary | 需求 ID、仓库、commit/PR、背景、方案、结果、关联知识和访问范围 |

### 4.4 条目示例

以下仅为结构示例，不代表技术结论已经被验证。

```json
{
  "id": "K-000123",
  "revision": 1,
  "type": "pitfall",
  "presentation": "article",
  "title": "特定表格布局下的列宽异常",
  "claim": "在已验证环境下，显式设置列宽可解决该复现用例的问题。",
  "knowledge_role": "experience",
  "rationale": {"text": "验证记录保存了触发条件与修复前后对照，最终代码本身未保留该排障过程。", "evidence_ids": ["EV-0008"]},
  "invalidation_triggers": ["表格组件升级", "容器布局变更"],
  "capture_assessment_id": "CA-0008",
  "context": {
    "preconditions": ["启用文本省略", "使用来源用例中的容器布局"],
    "dependency_constraints": [{"name": "table-component", "version": "1.2.3"}],
    "exclusions": ["其他版本尚未验证"],
    "verification_method": "运行来源记录中的最小复现并比较渲染结果"
  },
  "scope": {"tenant_id": "team-a", "domain_id": "ads", "repo_ids": ["repo-1"], "layer": "3"},
  "publication_status": "published",
  "maturity": "verified",
  "freshness": "current",
  "serving_status": "enabled",
  "owner_id": "owner-1",
  "evidence_ids": ["EV-0008"],
  "validation_ids": ["VAL-0012"],
  "supersedes": null,
  "created_at": "2026-09-11T02:00:00Z",
  "last_validated_at": "2026-09-11T03:00:00Z",
  "review_due_at": "2026-12-11T03:00:00Z"
}
```

标题、内容、适用条件和来源定位为发布必填。无法证明适用范围的候选退回补充，不能靠标签推断适用性。来源使用稳定的服务端引用及版本，不采用只有贡献者本机才能找到的临时文件路径作为唯一证据。

### 4.5 知识增量与采集判定字段（MVP 必需）

CaptureAssessment 是候选判定记录，存储在受控元数据中；所有进入候选池的条目均需关联一份记录，包括最终没有生成知识的情况。它不是新的知识主类型，也不是正确性评分。

| 字段 | 要求 |
| --- | --- |
| question | 独立的场景问题，包含必要条件，不包含候选答案或暗示 |
| checked_context | 仓库及 commit、已查文件/测试/文档版本、访问范围、查询和预算实际用量；未查阅不得填写为已查阅 |
| assessment_method | human_review 或 isolated_check；记录执行者/模型及规则版本 |
| discoverability | code_recoverable / authoritative_source / missing_context / inconclusive，含判断依据 |
| baseline_answer | 检查者从现有材料得出的答案及引用；没有答案时明确说明原因 |
| knowledge_delta | 候选相对于基线新增的最小信息；没有增量时为空 |
| claim_evidence_map | 将增量中的每项事实与来源 ID、版本和定位绑定；明确哪些只是推断或待确认 |
| omission_consequence | 缺少该信息会造成的具体错误或重复工作，不得编造事故及收益 |
| priority | P0 / P1 / P2；按缺失代价排序，不代表置信度、成熟度或访问权 |
| disposition | index_only / link_existing / knowledge_candidate / needs_confirmation / discard |
| review | 决定人、时间、理由、需要补充的问题；人工修改机器判定时保留原记录 |

已发布 KnowledgeEntry 新增：

- `knowledge_role`：experience（有增量的经验）或 authoritative_mirror（经批准的权威规范镜像）。导航项保存在单独的索引记录中，不作为经验条目计数。
- `rationale`：结论依据及证据 ID。未知原因明确写“原因待确认”，禁止依据最终代码倒推历史动机。
- `invalidation_triggers`：版本、规则、依赖或环境发生什么变化需要复核；未知时写明并由 owner 指定复核条件。
- `capture_assessment_id`：发布对应的判定记录；实质内容修订需重新判定。
- `alternatives`：仅对确有取舍证据的决策记录候选方案、拒绝原因和来源；不强制为所有条目虚构备选方案。
- `enforcement`：建议承载方式（test / lint / contract / pipeline / documentation / none）、关联任务/产物、状态（proposed / implemented / verified）。建议不等于已经执行。

经验发布必须存在非空 knowledge_delta 和对应证据；其他必填与人工审核规则仍适用。规范镜像允许增量为空，但必须提供权威来源、同步责任人和镜像理由。仅凭模型推测填满字段不能通过审核。

## 五、生命周期与验证机制

### 5.1 四个独立状态维度

| 维度 | 状态 | 说明 |
| --- | --- | --- |
| 发布状态 | candidate / in_review / published / rejected / withdrawn / archived | 是否完成发布流程 |
| 成熟度 | draft / verified / proven | 经审核的验证程度 |
| 时效性 | current / review_due / stale / unknown | 是否仍符合当前环境 |
| 检索开关 | enabled / suspended | 是否允许普通检索返回 |

普通检索只返回 `published + enabled` 且满足时效与适用规则的条目。审核通过但尚无有效验证的条目可以保持 draft，返回时标记“未完成验证，不作为确定结论”。

### 5.2 发布状态流转

- candidate → in_review：字段完整、权限检查及敏感信息检查通过，并完成 §6.8 分流；仅 knowledge_candidate 或经批准的规范镜像进入正文发布审核。needs_confirmation 留在 candidate 待补充。
- in_review → published：有权审核者批准；MVP 全部采用人工审核。
- in_review → candidate：需要补充信息。
- in_review → rejected：无价值、无法验证或不能合法共享。
- published → withdrawn：确认错误、不允许继续共享或被替代。
- published → archived：不再维护且无继续活跃检索价值。
- 已发布条目的正文修订创建新 revision，经审核后生效；历史版本保留用于审计。
- 撤回或归档后恢复必须重新审核。错误反馈可以先将检索开关置为 suspended，再完成内容裁决。

### 5.3 成熟度标准

| 等级 | 进入条件 |
| --- | --- |
| draft | 已形成可理解的结论，但没有足够的已审核验证证据 |
| verified | 至少一次针对该结论和适用条件的有效验证，由非提交者审核确认 |
| proven | 至少两次独立任务验证，涉及至少两名验证者；跨项目适用的知识还需至少两个适用项目 |

单项目知识可以在同项目不同独立任务中达到 proven；不能为了成熟度强制跨项目。团队规则的验证是负责人确认其权威来源、生效范围及当前有效性，不要求用运行测试证明组织决策。

LLM 置信度不映射为正确概率，draft/verified/proven 不再绑定 0.5、0.8、0.9 等概率区间。

实质修改结论、前置条件或适用范围时，新版本需重新评估成熟度；旧版本证据只能经审核后用于新版本。排版修改可以保留成熟度，但记录审核依据。

### 5.4 使用与验证事件

依次区分 `retrieved`（返回）、`cited`（产物引用）、`applied`（实际采用）、`validation_submitted`（提交验证）、`validation_accepted`（审核有效）。

前三级事件只更新使用统计。只有通过审核的验证记录触发成熟度重算。任务最终完成、测试整体通过或 Agent 自报“已采用”，均不足以单独证明某条知识正确。

验证结果为 success / failure / inconclusive。失败证据触发复核；严重反证可先暂停检索。无结论记录不增加成功验证次数。重复上报、同一任务内多次引用不得充当独立验证。

### 5.5 时效与复核

使用热度、可信程度和时效分别保存。长期未引用仅降低热度，不自动降低成熟度。

依赖升级、业务规则变更、来源删除或明确反证触发复核。定期复核周期按类型和 owner 配置，试点默认 90 天；到期先标记 review_due 并提醒。版本明确不兼容的知识不作为当前任务建议；stale 默认不进入普通检索。

灾备、低频业务流程等重要条目允许 owner 标记 critical，避免按热度归档。归档和删除是不同操作。

## 六、知识获取与沉淀

### 6.1 MVP 获取路径

1. 负责人导入已有规范、决策和已解决问题。
2. 开发者显式提交选定会话片段、PR 或交付产物。
3. 客户端提供预览并生成最小候选包。
4. 服务端异步提炼，生成候选结论与逐项证据定位。
5. 按 §6.8 检查代码/文档可发现性及新增信息，形成 CaptureAssessment；按结果转为导航、权威来源链接、知识候选或待确认。
6. 审核者核对基线答案、知识增量、条件、证据与相似条目后发布；无增量且不属于规范镜像的内容不发布为经验。

冷启动不固定限制为 13 条。以覆盖试点评测任务为目标，优先整理 30—50 条有来源的高价值知识；实际数量按样本覆盖调整。代码只能证明当前实现，不能自动证明它是推荐规范。

### 6.2 后续自动采集

自动采集必须由团队启用并向成员展示采集范围。客户端支持暂停采集、排除仓库和内容预览；不读取个人偏好文件、不采集密钥及无关个人会话。

信号包括报错、修复验证、明确架构取舍、新业务约束、人工标记，以及“不能这样做，因为”“曾试过但撤回”“仅在某条件下例外”“必须先做再做”等因果、例外和顺序表达（见 §6.8.2）。重复编辑和工具调用次数只能作为弱信号，不能独立证明知识价值。正常完成的架构决策同样可以成为候选。

统一候选规则：满足任一有效强信号，或弱信号组合达到经试点评估的阈值即进入候选池。单次会话中的重要故障不因轮数不足被排除。具体阈值是可配置假设，需用标注样本评估精确率和遗漏率。信号仅证明值得检查，不证明值得发布；所有来源仍须经过 §6.8 的知识增量检查。

### 6.3 触发、聚合与去重身份

支持显式提交、工作流结束提交，以及后续的会话事件与离线批次。三者使用同一候选标准。

优先通过 task_id、PR 和 commit 关联来源；repo + branch 仅作辅助，不能把同一分支上不相关需求强行聚合。采集事件包含 tenant、repo、session、event_id、时间和内容哈希。工作流维护已覆盖的源事件 ID，离线处理只处理未覆盖部分。

会话边界由客户端显式结束事件或可配置空闲规则识别；崩溃恢复后允许补报。不同客户端由适配层转换为统一事件，避免依赖某一种工具调用名称。

### 6.4 本地与云端职责

| 位置 | 职责 |
| --- | --- |
| 客户端 | 授权范围识别、选择/预览、脱敏、轻量信号检查、打包、可靠上报 |
| 服务端 | LLM 提炼、候选评分、相似项比较、审核队列、发布和索引 |

MVP 不要求本地执行 LLM 摘要。快速响应目标指后台任务入队，不将 LLM 提炼承诺为 100ms。提交上限建议为每包 256KB UTF-8 数据；超限要求拆分或明确裁剪，不能静默丢失验证条件。

工作流 ARCHIVE 提交的是证据包，可附结构化候选；权威提炼和发布仍在服务端完成。服务返回 accepted 表示接收，不表示知识已发布。

### 6.5 质量路由

五维评分保留 confidence、source_fidelity、reusability、completeness、actionability。其中 confidence 是模型自评，source_fidelity 仅反映与来源一致性。每项采用 1—5 分及文字依据，不视为客观正确概率。

统一路由顺序：

1. 格式、权限或敏感信息检查失败：拒绝或隔离，给出可操作原因。
2. 完成 §6.8 可发现性与增量检查：可恢复事实转索引，已有权威内容转链接；无价值内容结束处理，均保留分流记录。
3. 检查未完成、增量缺乏证据、缺少条件/owner 或存在矛盾：补充信息／深度审核，不能默认作为隐藏知识发布。
4. 有证据的知识增量或符合 §4.5 的规范镜像，且无阻断项：进入普通审核；按 P0/P1/P2 安排顺序，五维评分辅助排序。
5. 审核通过：发布；不通过：退回或拒绝。采集优先级不能豁免证据及成熟度要求。

MVP 无自动发布分支，消除高 confidence、低 overall 无路由的遗漏。后续自动发布必须另行定义风险类别、标注集、误发布阈值、抽检比例和停用条件，不预设 89% 自动通过率。

### 6.6 语义去重与冲突

相似度仅筛出比较候选，不决定自动合并。MVP 可以用关键词、规范化标题与字段比较完成候选发现，无需提前依赖向量库。

依次比较授权范围、实体与版本、前置条件、结论方向和证据独立性：

- 完全重复的来源事件：幂等去重。
- 条件和结论一致：提出合并建议，由审核者批准。
- 条件不同、结论不同：独立保留，建立关联或版本关系。
- 条件相同、结论相反：标记冲突，必要时暂停检索，交 owner 裁决。

证据不得因合并而扩大可见范围。原条目 ID 保留重定向或替代关系，历史引用仍能解释。

### 6.7 历史需求复用

后续从有明确结果和稳定来源的需求生成摘要，不以代码变更行数或是否 Bug 修复决定价值。摘要记录环境、约束、方案、结果及 commit，检索同时考虑相关性和版本兼容性，时间新近性只作排序因素。

不承诺相邻需求具有固定复用比例；该假设通过试点验证。

### 6.8 优先沉淀代码难以揭示的知识（核心执行规范）

#### 6.8.1 优先对象与边界

以下是“知识增量的来源维度”，通过既有五类 type 表达，不新增类型枚举。

| 优先对象 | 普通代码事实 | 优先保留的增量 | 常用 type |
| --- | --- | --- | --- |
| 决策取舍 | 当前使用方案 A | 不采用 B 的原因、当时约束、重新选型条件 | decision |
| 业务约束与例外 | 分支判断和状态字段 | 规则目的、特殊例外、生效范围、确认人 | model / guideline |
| 外部系统限制 | 接口调用与参数 | 文档未表达的行为、实际限制、版本及验证方法 | pitfall / guideline |
| 排障与失败路径 | 最终修复代码 | 复现条件、无效尝试、已证实根因和修复对照 | pitfall |
| 变更与协作顺序 | 模块静态依赖 | 上线/迁移次序、需要同步的角色、遗漏后果 | process |

目录列表、函数签名、普通 CRUD、语言基础用法等默认转代码索引。若代码跨多个仓库难以定位，先改善导航，不能仅因搜索困难就断言存在新的业务知识。已批准的组织规则、现有 ADR 和接口文档优先引用原来源，不另造相互漂移的正文副本。

#### 6.8.2 捕获时机与证据完整性

- 用户纠正 AI：保存错误方案、明确的纠正原因及适用条件，不能只保存“不对”。
- PR/设计评审：保存候选方案、取舍依据和实际批准的决定，讨论中的提议不能当作最终决策。
- 需求澄清：保存业务例外和确认人；未经确认的口头猜测进入 needs_confirmation。
- 排障完成：保存复现环境、失败路径、最终变更及针对性验证；修复成功但根因不明时，只描述已观察的修复效果。
- 上线/迁移：保存前置条件、顺序、回退边界与负责角色；不采集无关私人信息。

在归档时可集中显示一个可选补充项：“本次是否有代码没有表达、但下一位开发者必须知道的约束或取舍？”有则提交证据，无则结束；不按每个候选反复打断开发者。后台提炼与等待补充不阻塞已完成的开发任务。

#### 6.8.3 可发现性对照与分流算法

所有候选 MUST 经下列判断；MVP 可以由审核者手工完成并留痕，不要求为每条候选启动独立模型任务。自动检查作为可替代执行方式，其服务端访问范围必须遵守第十章。

1. **提出中立问题**：根据任务与条件描述需要回答的问题，不把候选答案、历史失败结论或知识增量写入问题。
2. **检查现有材料**：使用固定 commit 的相关代码、测试及已授权权威文档作答，记录引用。采用隔离模型检查时，不提供提炼会话、候选正文或其他答案线索，不能复用提炼过程的隐含记忆。为该检查单独设定时间/token/工具预算并记录实际使用量；不得冒用 §7.4 的消费预算掩盖提炼成本。
3. **识别实际增量**：比较候选与有依据的基线答案；将可恢复的实现细节剥离，只保留原因、例外、外部约束、失败证据等差异。模型答对但无依据的猜测不算可靠恢复。
4. **核对新增断言的证据**：每项增量都应有来源。代码可以证明当前行为，不能单独证明当初为何这样设计。修复发生在某次改动之后也不自动证明因果关系。
5. **按下表分流并记录缺失代价**：不同子结论可拆成不同候选，避免一个有价值的原因夹带大量代码复述。

| 判定 | disposition | 必需动作 |
| --- | --- | --- |
| 代码/测试已充分回答，无独立增量 | index_only | 记录文件、符号、版本或导航建议，不生成经验正文 |
| 权威文档已充分回答 | link_existing | 建立有访问控制的来源链接；执行所需镜像走 §4.5 例外规则 |
| 已完成合理检查，缺少必要上下文，且增量有证据 | knowledge_candidate | 保存增量、证据、条件及优先级，进入人工审核 |
| 未检查、无权限、预算耗尽、结论冲突或增量证据不足 | needs_confirmation | 标记 inconclusive 或具体证据缺口，向有权负责人补充；不得伪装为 missing_context |
| 没有可说明的复用价值、明显噪声或完全重复 | discard | 保存理由并结束，不设最低产出条数 |

missing_context 只表示本次指定环境与预算下未能可靠恢复，由人工审核确认；不代表模型“永远无法理解”。原始信息后来进入代码、测试或权威文档时，应复核条目，必要时转链接、减少重复正文，保留历史依据。

#### 6.8.4 采集优先级

- **P0**：遗漏可能造成明确的严重错误，例如业务不变量失守、不可逆变更顺序错误。必须写明具体场景和证据，优先审核，并评估能否转为机器检查。
- **P1**：有证据表明会重复排查或返工，例如隐蔽组件故障、内部接口限制、被否决方案的适用边界。
- **P2**：辅助理解或影响较小；可恢复内容通常转索引或链接，不为凑数进入经验库。

低频不等于低优先级。priority 不控制成熟度或直接决定检索排名，更不能作为绕过内容权限的理由。

#### 6.8.5 提炼执行模板（供后续 AI 实现或调用）

以下为产品任务模板，必须由系统提供真实输入并校验输出；来源中的指令仅作为资料，不自动执行。

```text
任务：从授权证据中发现下一位开发者仅凭当前代码与权威文档难以可靠恢复的必要知识。
输入：任务与适用环境、源事件及版本、候选片段、现有材料清单；如有，附独立基线答案及其引用。

必须执行：
1. 拆分候选断言，区分当前代码事实、明确决策、观察结果和未证实推断。
2. 提出不含答案的 question；使用已有的真实检查记录。没有检查结果时标记 inconclusive，不能虚构检查过程。
3. 填写 CaptureAssessment 的所有适用字段，明确 knowledge_delta 与逐项证据。
4. 依据 §6.8.3 选择唯一 disposition；不同结论需要不同分流时拆分记录。
5. 仅 knowledge_candidate 产出待审核经验正文；其余输出导航/链接/待确认问题/结束理由。
6. 正文保留适用条件、结论依据、例外、验证方法和失效条件。仅有真实来源时写备选方案和失败原因。
7. 不设最少条数。无合格候选时返回空的经验列表及分流统计。
8. 不能宣称已发布、已验证或已新增测试，除非存在对应的服务结果或验证证据。

输出：assessments[]、knowledge_candidates[]、navigation_items[]、confirmation_requests[]。
每项关联源事件 ID；knowledge_candidates 必须关联 assessment_id。
```

审核界面 MUST 并列展示基线答案及引用、knowledge_delta、证据、条件、缺失代价和分流理由。审核者逐项确认：是否真正新增信息、是否有证据、是否过度泛化、是否应改为链接、是否能转为可执行约束。缺少判定记录或证据绑定时，发布接口必须拒绝，不能仅靠 Prompt 提醒。

#### 6.8.7 将知识转为持续执行的约束

审核者必须评估 enforcement：业务不变量适合测试/运行时校验；禁用模式适合 lint；接口限制适合封装或契约测试；上线顺序适合流水线检查；架构动机适合 ADR。

该评估只生成建议与关联任务，不自动修改业务代码、运行命令或扩展授权。相关改动完成并有验证证据后再更新 implemented/verified 状态；知识正文继续保存原因、来源与适用条件，并链接实际测试或配置。未实施不得宣称约束已得到保障。

## 七、知识检索与消费

### 7.1 查询流程

身份验证 → 服务端计算可访问集合 → 按仓库与环境过滤 → 检索候选 → 适用性判断及排序 → 再检查当前权限和条目状态 → 按预算返回。

用户传入的 repo/domain/scope 是请求条件，不是授权凭据。global 指当前身份有权访问的团队通用知识，不是系统全库。

### 7.2 排序与强制规则

项目相关性、适用版本、证据程度、来源权威性和时效共同参与排序。仓库知识优先但不采用“找到三条就停止”，以免漏掉必须遵守的团队约束。

团队强制规范使用受控配置通道单独加载，不依赖普通检索碰巧命中。规则正文仍有权威知识 ID/版本；客户端配置可以包含必要的规则内容，因此不再承诺本地绝无知识内容。

推荐性知识与团队强制规范分开显示。出现无法解决的规则冲突时返回冲突状态，并由负责人裁决，不能通过排序掩盖冲突。

### 7.3 返回契约

`search-knowledge` 返回条目 ID、版本、标题、关键结论、适用条件、成熟度、来源摘要/授权链接、匹配原因、截断标记，不默认返回完整文档。

`get-knowledge` 按 ID 获取授权范围内的完整条目；指定历史版本仅用于有权限的历史查看，并标记其当前状态。已撤回内容在普通工具中不返回正文。

零结果是合法结果。服务区分无适用知识、查询信息不足、预算限制和服务故障，但不通过原因泄漏未授权知识是否存在。模型不得将查询失败表述为“团队没有相关规范”。

### 7.4 预算与版本

默认每次最多 5 条、总返回上限建议 4000 tokens，每个任务最多 3 次自动检索；客户端可申请更高预算，服务端设硬上限。采用服务配置指定的 tokenizer 计算并记录预算，不使用行数或字符数替代。

必要的适用条件优先保留，无法容纳时返回摘要与展开提示，不输出脱离条件的结论。来源链接和补充获取也消耗查询预算。

引用必须记录知识 ID 和 revision。权限、发布状态与撤回信息在返回前重新校验；索引更新即便滞后也不能使撤回正文继续返回。

### 7.5 反馈入口

开发者可标记“有帮助／无帮助／不适用／疑似错误”，补充原因或验证记录；提供查看来源、提交修订和查看处理状态的入口。反馈不直接提高成熟度。

### 7.6 消费侧如何利用知识增量

对于决策、排障、业务规则和变更任务，查询应包含当前版本、环境、意图以及需要确认的原因/例外，不能只查实体名。响应在预算内优先保留与任务相关的 knowledge_delta、rationale、适用条件、例外及验证方法；返回这些字段时仍遵守来源与内容授权。

消费 Agent 必须区分“代码当前怎么实现”和“团队为何要求这样做”。只有当前适用且有证据的内容才可作为建议依据；推断或待确认原因不得表述为确定事实。发现代码与已发布规则不一致时记录冲突，不能仅因代码当前如此就覆盖规则，也不能盲目沿用历史结论。

若问题只是文件位置或函数定义，优先代码工具/导航索引；若问题涉及取舍、外部约束或失败经验，再检索经验条目。已知必须加载的团队规范仍按 §7.2 执行，不受此按需建议限制。

## 八、客户端接入与配置中心

### 8.1 MVP 接入流程

1. 平台管理员配置身份提供方和知识服务地址。
2. 开发者安装首个受支持的适配器，完成登录与仓库绑定。
3. 服务端核验用户与仓库授权，返回配置版本及可用工具。
4. 适配器通过宿主支持的配置机制注册工具与入口，进行连通性检查。
5. 后续打开已绑定项目时自动检查受控配置更新。

不将首次接入称为“零分钟”。试点目标为前提就绪后 10 分钟内完成；记录实际成功率和耗时。具体首个宿主和版本由试点启动表冻结，未经验证不宣称兼容全部工具。

### 8.2 本地内容

允许保存：知识网关说明、宿主配置、受控团队规则、用户个人偏好、临时检索结果与未发送队列。团队全量知识库不克隆到开发者设备。

网关是使用说明，工具是否可调用由宿主注册和服务认证决定。约 200 行仅作为可读性参考，不作为上下文成本指标。

个人偏好不能覆盖团队强制策略。云端配置写入采用临时文件校验后原子替换，保留最近可用版本，不静默覆盖开发者自定义区域。

### 8.3 配置优先级

安全和访问控制策略始终强制生效，不参与用户覆盖。普通配置按：授权内显式业务域选择 → 仓库映射 → 授权人群配置 → 团队默认值。

显式选择业务域必须验证仓库映射与用户权限。一个仓库映射多个业务域时要求选择有效上下文，不能按名称猜测权限。

配置对象具有版本、发布人、兼容宿主范围、校验信息和回滚指针。MVP 下发受支持字段；可执行 Skills 分发后置，不能作为普通知识内容直接执行。

## 九、系统架构与接口

### 9.1 组件职责

```text
客户端适配器
  ├─ 身份与仓库绑定、配置加载
  ├─ 查询与反馈、引用记录
  └─ 提交预览、脱敏、可靠队列
             │ 认证后的请求
             ▼
知识服务 / MCP 接口
  ├─ 授权与适用性过滤
  ├─ 查询与条目获取
  ├─ 候选接收、任务状态和事件幂等
  └─ 审核、发布、撤回、配置版本
             │
  ┌──────────┼───────────┐
内容版本库   元数据与任务库   检索索引
Markdown/Git 状态/ACL/事件   可重建的派生数据
             │
异步提炼 Worker + 审核后台 + 治理任务
```

Git 用于内容版本与可迁移性，不作为高频使用事件或并发任务队列。元数据与任务库采用事务存储，具体产品在技术设计中选择；不再要求无数据库。证据正文使用访问受控的来源系统或独立证据存储，敏感原始会话不直接提交到长期 Git 历史。

### 9.2 一致性规则

发布过程先写不可变内容版本，再通过事务激活知识 revision 和状态，同时写入待索引事件；索引失败可重试。没有被激活的内容版本不对外可见。

元数据为当前权限和可服务状态的权威源；查询索引为派生数据。服务读取索引后重新检查权威状态。内容版本写入失败则不得激活，元数据提交失败产生的孤立版本由后台清理。

MVP 内容仓库写入采用受控串行写队列；对象编辑使用 revision 乐观锁。引用和验证事件通过唯一键去重。

### 9.3 核心接口契约

| 接口 | 关键输入 | 关键输出 |
| --- | --- | --- |
| search-knowledge | query、repo_id、environment、scope、limit、token_budget | items、query_id、状态、预算信息 |
| get-knowledge | id、可选 revision | 授权正文、当前状态、来源 |
| ingest-knowledge | idempotency_key、source_event_ids、repo_id、evidence、可选候选 | contribution_id、accepted/duplicate、处理状态 |
| get-contribution | contribution_id | 状态、disposition、判定摘要、退回原因、发布 ID（均经授权） |
| record-usage | event_id、task_id、knowledge_id、revision、event_type | recorded/duplicate |
| submit-validation | event_id、知识版本、方法、环境、结果、证据 | validation_id、待审核状态 |
| submit-feedback | 知识版本、类型、说明 | feedback_id、处理状态 |
| get-config | repo_id、client_version、current_config_version | 配置差量或未变更、兼容性状态 |

客户端可提交候选与证据，但不能把其自报 discoverability 或 priority 当作已审核结论。CaptureAssessment 由服务端流程生成或由有权审核者填写；发布接口强制校验 §4.5 和 §6.8.5 的要求。

MVP 的审核发布、撤回和 lint 操作通过受控管理接口提供，不作为所有编码 Agent 默认可调用的写工具。`search-history-requirements` 为后续扩展。

统一错误类别：未认证、无权限、输入不合法、版本冲突、限流、暂时不可用。响应包含 request_id 和可重试标志，不包含密钥或未授权内容。

### 9.4 可靠性与降级

- 幂等键在租户内唯一。同键同载荷返回原结果，同键不同载荷返回冲突。
- 暂时性失败采用指数退避和随机抖动；MVP 默认最多自动重试 5 次，之后进入可见的待处理队列。
- 客户端未发送队列默认保留 7 天，用户可查看、删除和手动重试；到期清理前给出状态提示。
- 查询默认 3 秒超时，失败不阻塞普通编码；依赖强制规范且无法确认其有效版本的操作应提示校验未完成，不能伪造通过。
- 配置更新失败保留最近已验证版本并标记状态；已知撤销的配置不能继续回退使用。
- 普通检索结果只在当前会话中临时使用。重新执行知识相关操作需检查当前权限与状态；撤回无法抹除已产生的本地输出，需保留更正提示与追踪能力。
- 任务与索引可重建；备份恢复须演练，记录恢复时间和数据缺口。试点建议 RPO 24 小时、RTO 4 小时，须与团队可接受损失核对。

## 十、数据边界与治理

### 10.1 访问与数据保护

使用受认证的加密通道，不采用“内网自动可信”。认证主体与服务端团队、业务域、仓库映射共同决定权限；逻辑隔离由服务端强制执行。物理独立部署是特定需求下的部署选项，目录隔离本身不是权限保证。

检索过滤、证据查看、审核、导入、导出和后台搜索均执行相同授权。权限收回后，对后续请求立即生效；缓存与派生索引不能绕过检查。

采集前执行本地敏感信息检查，服务端再次检查；疑似密钥或不允许上报内容进入隔离或拒绝流程，不交给模型继续处理。日志默认记录 ID、状态与耗时，不记录完整会话和知识正文。

外部模型调用范围、供应商处理方式及部署地域在试点启动前确认；未完成确认的内容不外发。

### 10.2 数据保留

| 数据 | MVP 默认策略 |
| --- | --- |
| 未发送本地队列 | 最长 7 天，可提前删除 |
| 服务端原始证据包 | 最长 30 天，审核完成后只保留必要证据片段和稳定引用 |
| 已发布知识及审核依据 | 有效期间保留，撤回后按团队保留策略处理 |
| 去正文使用事件 | 默认 90 天，后续仅保留聚合统计 |
| 操作审计 | 默认 180 天，按团队要求调整 |

上述为设计默认值，试点前确认。删除请求需覆盖正文、原始证据、索引、缓存和备份生命周期；Git 中误入敏感内容不能靠新增删除提交解决，需要受控历史清理和备份处理。需要保留的最小审计记录不保留已删除敏感正文。

来源消失时标记证据不可用并复核；不能继续把不可验证链接当作有效证据。

### 10.3 Prompt 与执行边界

返回资料明确标记为知识内容。资料中的“执行命令”“忽略规则”等文本不能自动改变 Agent 权限。工具调用授权由宿主及服务端执行；知识正文不能触发安装、上传、配置修改或发布动作。

规范配置和可执行技能使用独立的受控发布机制；内容贡献权限不等于执行配置权限。

### 10.4 Lint 与运营

每天运行结构校验、来源可用性、待复核、孤立索引与重复候选检查。结构索引可自动修复；正文合并、成熟度变化和共享范围变化在 MVP 必须经审核。

审核队列展示等待时间、owner、退回原因和冲突。试点目标为普通审核 2 个工作日内首次处理；超时提醒责任人，不能靠自动发布清空积压。

审计记录贡献、审核、发布、撤回、权限变更及配置变更。追加日志用于追踪，不宣称普通 Git 日志具备不可篡改保证。

## 十一、指标、评测与验收

### 11.1 指标定义

| 指标 | 计算或评价方法 | 用途 |
| --- | --- | --- |
| 查询有结果率 | 返回至少一条适用结果的查询数 / 总查询数 | 覆盖观察，不单独设越高越好的目标 |
| Precision@k | 标注为相关且适用的返回条目 / 实际返回条目 | 检索质量；空结果另行统计 |
| Recall@k | 返回的相关条目 / 标注集中的相关条目 | 需已标注相关集合；无相关答案样本不纳入分母 |
| 无答案误返回率 | 应无答案却返回建议的查询 / 无答案查询 | 防止强行填充 |
| 适用条件错误率 | 含版本或场景错配建议的查询 / 有返回查询 | 监控错误使用 |
| 有证据知识占比 | 有可访问且可追踪依据的已发布条目 / 已发布条目 | 发布完整性 |
| 验证成功率 | 经审核成功验证 / 经审核的确定性验证 | 不含 inconclusive，始终报告样本数 |
| 重复问题发生率 | 同类问题再次发生任务 / 适用任务 | 团队复用效果 |
| 单条有效知识成本 | 提炼及审核成本 / 最终保留的有效条目 | 运营可持续性 |
| 查询 P95 / 失败率 | 服务端与客户端分别采集 | 日常体验 |

引用量、知识总量与热度仅为辅助统计，不代替质量与业务收益。

### 11.2 离线评测

试点前建立至少 60 个标注查询，建议包括 30 个可回答样本、15 个无答案样本、10 个版本／条件冲突样本、5 个权限隔离样本。每条记录预期适用知识、禁止返回内容和判定理由；授权边界另有完整自动化测试矩阵，不以 5 个样本替代。

由领域负责人标注，另一名成员复核分歧。保留固定评测集与未参与调优的留出样本；不能把同一来源的近似查询拆到训练与留出两侧造成虚高结果。

### 11.3 MVP 建议质量门槛

- 已发布条目必填字段、owner 和可追踪来源覆盖率 100%。
- 所有已知越权测试均通过；测试中出现任何内容泄漏，阻断试点扩大。
- 有答案样本的宏平均 Precision@5 ≥80%、Recall@5 ≥70%。
- 无答案样本误返回率 ≤10%，版本条件冲突样本中不得把已知不兼容结论作为直接建议。
- 撤回、重复提交、证据去重、配置回滚和权限收回场景全部通过。
- 1000 条知识、10 个并发查询的约定测试环境下，查询端到端 P95 ≤2 秒，错误率 ≤1%；不包含 LLM 提炼耗时，环境与网络条件必须随报告给出。

有答案样本若返回零条，其 Precision 和 Recall 均按 0 计入宏平均，避免只回答少数简单问题抬高质量指标。返回不足 5 条时，Precision 分母采用实际返回条数，Recall 仍依据完整标注的相关集合。

门槛是试点建议值。启动前冻结阈值与计算方法，避免看完结果再调整口径。小样本指标同时报告分子、分母，不暗示统计确定性。

### 11.4 实际交付效果

选择至少 20 个可比较真实任务，按复杂度、开发者经验和任务类别记录基线；条件允许时随机分组或交叉使用，控制熟悉度和知识传播影响。

比较启用与未启用知识服务时的有效工作耗时、返工次数和重复排查，同时记录错误建议与审核投入。以耗时中位数改善 15% 且返工不增加作为试点收益假设；该阈值不是收益承诺，小样本仅用于决定是否继续验证。

通过条件：离线质量和权限门槛满足，且真实任务出现有证据的复用案例、未出现不可接受的负面影响。若收益不明确，保持试点范围，优先排查知识覆盖、检索与使用方式，不直接扩张自动采集规模。

### 11.5 知识增量专项评测与验收（MVP 必需）

在 §11.2 检索集之外，先建立至少 20 条历史候选的人工标注集，每种 disposition 至少 4 条；由领域负责人标注、另一成员复核，记录来源、预期增量和理由。额外覆盖规范镜像、检查预算耗尽、无权限、模型猜中但无依据、混合结论需拆分、修复成功但根因不明等边界。该小样本用于规则校准，不证明自动采集已达到生产可靠性。

| 测试 | 通过标准 |
| --- | --- |
| 纯代码复述 | 分流至 index_only，不发布为新增经验 |
| 已有权威文档 | 分流至 link_existing；需要镜像时明确例外依据与责任人 |
| 有来源的隐性约束 | 保留相对基线的具体增量、条件、来源及失效条件，进入审核 |
| 无来源的原因推测 | needs_confirmation，不得包装成已知原因 |
| 未查阅／预算不足／无权限 | 标记 inconclusive；不得填报已检查或扩大访问范围 |
| P0 但证据不足 | 优先补充确认，仍不能绕过发布校验 |
| 无合格候选 | 允许空经验列表，保留分流统计 |
| 直接调用发布接口跳过 Prompt | 缺少合法判定和证据时被拒绝 |
| 消费摘要预算有限 | 不丢失会改变结论的前置条件和例外 |
| 约束固化建议 | 未执行时保持 proposed，不声称测试/流水线已经生效 |

建议记录以下指标，与 §11.1 的检索指标并行：

- **经验增量合格率**：抽检中确有证据支持新增信息的 experience 条目 / 抽检 experience 条目；规范镜像不纳入分母。
- **代码复述误入率**：抽检经验中可直接恢复且无独立增量的条目 / 抽检经验条目。
- **重要增量遗漏率**：标注为 P0/P1 且应进入知识候选却被转索引/丢弃的样本 / 所有此类标注样本。
- **未证实断言发布数**：无充分依据却被写成确定结论的已发布断言数量；已知用例中出现任何一例即阻断扩大试点。
- **分流与检查成本**：五类分流数量、inconclusive 占比、检查 token/时间、人工复核分钟数。不能用大量转待确认掩盖漏检或虚高准确率。

MVP 要求发布校验与上述确定性用例全部通过，经验判定记录与增量证据绑定覆盖率 100%。抽样合格率和遗漏率随样本数报告，启动前由团队冻结扩展门槛，不凭模型自评验收。

检验实际价值时，在相同代码快照、模型与工具预算下对照“代码＋现有权威文档”和“相同材料＋新增经验”，用未见过原始讨论的独立执行过程，比较约束违反、重复尝试、完成率、时间和成本。留出任务不得泄漏候选答案；记录全部失败，不能只展示成功案例。产出更多知识或消耗更多上下文不算收益。

## 十三、风险与应对

| 风险 | 检测方式 | 应对 |
| --- | --- | --- |
| 代码复述挤占经验库 | 增量合格率、误入率、分流成本 | 执行 §6.8 检查，代码事实转索引，权威内容转链接 |
| 将模型搜索失败误认为隐性知识 | inconclusive 比例、检查范围与证据抽检 | 有界检查留痕，人工确认增量，不以无结果证明缺失 |
| 错误经验形成循环强化 | 引用多但缺少有效验证；反证增加 | 引用与验证分离，暂停并复核 |
| 知识过度泛化 | 跨版本或场景误用 | 必填适用条件，范围扩大需审核 |
| 审核积压 | 队列时长和单条成本上升 | 减少低价值候选、优化证据，不自动放行 |
| 自动采集漏报／误报 | 标注样本检测指标下降 | 调整信号，保留显式提交入口 |
| 客户端接入困难 | 首次连接失败率高 | 先支持一个入口，适配器能力验收 |
| 服务故障影响编码 | 查询超时、重复重试 | 有界超时、可靠队列、明确降级 |
| 跨域泄漏 | 越权测试、权限审计 | 服务端统一授权，证据与索引同规则 |
| 知识污染执行流程 | 恶意指令测试 | 资料与执行配置分离，工具授权独立 |
| 检索规模增加 | 延迟与相关率恶化 | 按评测结果优化索引，必要时引入混合检索 |
| 维护投入大于收益 | 有效知识成本高、任务收益不明 | 缩小知识类型与场景，暂停范围扩张 |

## 十五、术语与资料说明

- 知识增量：相对于指定版本代码与授权权威资料，经检查仍需补充且有证据支持的必要信息；不等于新生成的一段文字。
- 可发现性检查：记录 AI 或人工能否在约定材料和预算下可靠恢复答案，检查不完整时结果为 inconclusive。
- 知识发布：候选经过审核后进入可服务状态。
- 知识验证：针对具体结论和适用条件，审核其支持或反对证据。
- 知识引用：产物中记录知识 ID/版本，不代表结论正确。
- 共享范围变更：修改知识可以被哪些主体访问，与成熟度独立。
- 知识撤回：阻止后续普通检索返回，保留必要历史追踪。
- MCP：本产品对编码客户端提供能力的接口方式之一；权限和业务正确性仍由服务实现。
