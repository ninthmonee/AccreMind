# 项目约束

在修改业务代码、依赖或构建配置前读取一次，并应用与任务相关的规则。纯分析、review、文档及仓库流程规则修改无需加载。
本项目的明确约定优先于通用技术 skill；用户对当前任务的明确要求优先。

## 变更边界

- 围绕已授权需求做最小改动，不顺带调整无关功能、样式、依赖或格式。
- 保留已有行为与接口；未经用户要求，不删除或隐藏已有按钮、菜单、快捷入口等功能。
- 先检索实际依赖、组件和封装，再选择实现；缺少关键信息时说明缺口，不编造 API。
- 依赖与语法以项目实际安装版本为准，不因通用文档使用较新版本就升级项目。
- 修复问题前先复现并根据日志、调用链或最小案例定位根因；修改后验证原问题及相关边界，避免只处理表面症状。

## UI 与项目封装

- 优先复用项目已有组件、hooks 和工具。新增前检索同类实现；现有实现能清晰扩展时优先扩展。
- 组件库使用 `antdv-next`，不回退到 `ant-design-vue`。新增组件或调整组件 API 用法前读取 `antdv-next` skill 和当前组件文档；仅样式调整无需查阅 API，不要求通读整个文档库。
- 弹窗/抽屉优先项目封装或 `vue-modal-provider`；表格查询、分页、排序与筛选优先已有表格封装和 `use-table-query`。
- 图表优先 `use-echarts` / `common-echarts`，避免在业务页面重复初始化和销毁 ECharts。
- 布局和交互同时考虑 Web 与 iPad，包括触控、横竖屏及键盘操作。
- 自研 UI 兼容日夜主题。`antdv-next` 自带主题适配，不额外覆盖其日夜主题样式。

## Vue 与数据流

- 使用 Vue 3 Composition API、`<script setup lang="ts">`，在安装版本支持且适合需求时使用 `defineModel` 等宏。
- 业务状态使用 `ref`，不新增 `reactive`；通用 Vue 资料的状态偏好不能覆盖本项目约定。派生状态使用 `computed`。
- Props 向下、事件向上；不直接修改父组件状态。Props、事件和共享上下文应有明确类型。
- 按职责、复用和逻辑复杂度拆分组件/composable，不为满足层数或组件数量而拆分。页面负责组合，复杂或复用逻辑放入 composable。
- 优先局部状态；确需跨模块共享时使用现有 Pinia store，并说明共享的必要性。
- 异步错误处理沿用 `await-to-js` 的 `to` 风格，避免业务代码中散落重复的 `try/catch`。

## API 与文档

- 接口函数名以 `Api` 结尾；沿用现有接口协议，新增接口设计遵循 RESTful 语义。
- API 和公共工具注释说明用途、关键参数、返回值及错误/边界约定；其余注释用于解释非显然的原因，不要求每段代码加注释。
- 菜单对应模块保留 `README.md`，说明职责、组件/数据流、关键依赖、使用方式和限制，内容按实际复杂度编写。
- 新增组件或 hooks 时在同目录补充或更新 `README.md`，说明用途、输入输出、使用方式与限制；同目录共用文档，无需每个文件重复一份。

## 验证与交付

- 根据改动范围运行相关类型检查、lint、构建或行为验证；纯规则/文档改动检查格式、链接和规则一致性即可。
- 声称完成、修复或检查通过前，须有针对当前改动执行的验证证据，并检查完整输出与退出码；部分检查通过不能代表全部通过。
- 汇报实际修改、验证结果和仍未验证的部分；验证失败不能仅凭错误文件未被修改就认定为既有问题，认定既有问题须有基线对照或其他证据。
- 保留用户当前工作区的其他改动，交付时使用简洁中文说明，不重复粘贴整份代码。
