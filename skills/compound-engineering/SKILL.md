# 复利工程

复用已有踩坑经验，并把本次验证得到的新知识留给后续开发。回复使用中文；项目规则与用户指示优先。

## 适用范围

- 修改项目代码、业务样式、依赖或影响运行的构建配置前，必须执行改前检索。
- 纯问答、分析、review、阅读及文档/规则修改不触发；由分析转为代码修改时再检索。
- 同一任务、相同改动范围内已检索的资料直接复用；范围或根因变化时补充检索。

## 改前检索

1. 从任务提取组件、库、错误信息与领域关键词，先查看 [INDEX.md](references/INDEX.md) 找到相关领域文件。
2. 使用 `rg` 搜索 `references/experiences/` 的 `meta`、`tags`、标题及正文，读取命中条目及必要上下文。按当前任务读取相关领域，不加载全部经验正文。
3. 核对条目适用的依赖版本、触发条件和验证状态。待验证或过时条目只能提供排查线索，不能当作已确认方案。
4. 在改代码前简要说明会影响本次实现的经验与适用限制，提供相关条目链接；无直接命中时一句说明即可，不要求固定输出模板。

路径相对本 skill 目录。例如：

```sh
rg -n -i 'vite|catalog|dependency' references/experiences/
```

## 验证与沉淀条件

- 按项目约定与实际改动风险验证：类型、构建、lint、测试或交互检查选用相关项。修复必须验证原问题，依赖/构建变更必须验证受影响的构建链。
- 验证失败或缺少关键证据时，先处理或说明限制，不把方案标为已解决。
- 只有新增可复用知识时才沉淀，例如可复现的根因、特殊边界或版本行为；常规实现、重复经验和纯文档规范无需新增条目。
- 写入已验证经验前，须有本次任务中用户对改动正确或问题解决的确认。已有明确确认直接使用，无需指定提问工具或再次索要确认；完成开发也不以等待确认作为结束前置条件。
- 用户尚未确认、问题未解决或验证不足的发现，如值得保留，只可标为“排查中/待验证”，写明已知证据和未验证部分；不得填写虚假的验证日期或宣称方案已解决。
- 用户要求跳过沉淀时不写入；不为每次任务强制生成经验。

## 写入与去重

沉淀前再次搜索相似记录，比较问题、根因、方案、场景与预防方式：相同问题优先更新已有条目，同一领域的不同条件补充明确的差异，独立问题才新建。保留已有适用场景和证据，避免用新场景结论覆盖旧场景。

- 写入对应 `references/experiences/` 领域文件。格式参考 [_TEMPLATE.md](references/_TEMPLATE.md)，领域汇总见 [experiences.md](references/experiences.md)。
- 条目应包含现象/背景、根因或适用条件、方案、最小复现或可运行示例，以及实际验证方法与结果。
- 保留现有 `meta` 字段：`type`、`tech`、`domain`、`severity`，已验证条目记录实际 `validated` 日期；版本敏感结论记录 `version` 与适用范围。待验证条目明确标注状态，不填 `validated`。
- `tags` 优先使用 [INDEX.md](references/INDEX.md) 的标准词，避免同义词分裂；必要的新词同步追加并说明理由。
- 新增领域文件或影响索引描述的条目时，同步更新 `INDEX.md` 与 `experiences.md` 中受影响的入口；不改无关经验。

## 版本与冲突

- 依赖升级后，本次涉及的版本敏感条目须复核；尚未复核的标“待复审”，不要仅凭 major 变化批量判定失效。
- 新证据与旧条目冲突时，先核对版本及场景。确认过时后标注废弃原因与替代链接，保留历史内容；重新验证有效后更新日期及版本。
- 项目统一约定归 `project-constraints`，Vue API 资料按需查阅 `vue`；这里记录具体坑位、变体和验证证据，通过链接引用已有资料。
