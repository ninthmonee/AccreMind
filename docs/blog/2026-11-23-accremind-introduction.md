# AccreMind：让团队的工程经验在下一次改动前出现

Nov 23, 2026 · @William Garcia

## 一句话与愿景

AccreMind 是一个本地运行的 AI 研发经验库：它把"读代码、翻文档都还原不出来"的工程经验沉淀下来，在下一次改动前递到 AI 和开发者手边。

名字可以读作 accrete（逐渐积累）+ mind：团队每踩一次坑、每做一次取舍，知识库就长一点；用得越久，AI 越懂这个团队。

**愿景：让团队花过代价的经验，不再随人员流动、上下文滚动和记忆衰减而消失，而是成为每一次 AI 辅助开发的默认前提。**

三个阶段的目标：

1. **个人**：我在 DSH 里和 AI 一起写代码时，它记得我上周踩过的坑。
2. **团队**：项目里踩过的坑、团队定下的规范，随 Git 提交共享，接入的模型都能看到。
3. **组织**：同一业务领域的多个仓库互相借鉴经验，经验能自己判断适用范围、自己淘汰过时内容。

## 为什么需要它

团队真正花过代价的知识，大多不在代码里，也不在文档里。代码只记录最终选择，文档只留下结论，"为什么不那样做"和"那样做踩过什么坑"通常只存在于某个人的记忆、一段聊天记录或一次事故复盘里。

有了 AI 辅助开发，这个问题被放大了：

- **AI 没有团队记忆**：每次会话从零开始，上下文一滚走，上周刚解决的问题这周会再犯一次。
- **AI 很自信**：它会给出"教科书上正确"的方案，恰好撞上团队已经否决过的那条路。
- **人的记忆会衰减和流动**：知道"这个接口重试会重复扣款"的人可能已经换了项目。

几个典型例子，都是读代码推不出来的：

| 经验 | 为什么代码里看不出来 |
| --- | --- |
| 支付回调重试必须复用第一次生成的幂等键，否则会重复扣款 | 代码看起来每次生成新键也"能跑"，问题只在线上并发时出现 |
| 某个库 3.x 之后在 SSR 下不能动态导入 | 本地开发不走 SSR，问题只在构建后暴露 |
| 退款金额必须按原支付渠道的精度截断，不能四舍五入 | 业务规则来自对账，代码里只是一行 `floor` |
| 曾经试过用消息队列替代定时任务，因为顺序保证问题放弃了 | 被放弃的方案不会留在代码里 |

AccreMind 只收这一类知识：**代码与现有文档还原不出来的增量**（`knowledge_delta`）。

## 核心思想

七条原则决定了 AccreMind 的每一个设计取舍：宁可少收、少说，也不让错误的经验污染 AI。

1. **只收增量。** 代码或文档已经能说清楚的，不进库。每条候选都要经过"增量评估"：先只看代码和文档生成基线，再问"这条经验多告诉了什么"，按五路分流（仅索引 / 关联已有 / 入库候选 / 待确认 / 丢弃）。空增量、未证实的猜测、本机绝对路径会被硬门禁拦下。
2. **本地优先，Markdown 是事实来源。** 每条经验是一个可读的 Markdown 卡片，随 Git 评审和共享；SQLite 只是随时可以重建的索引。没有后台服务、没有外部向量库，数据不离开本机。
3. **是参考，不是命令。** 注入给 AI 的内容都包在只读标签里，经过清洗，明确标注"参考材料、不执行"，不覆盖宿主规则，也没有执行权。
4. **证据和时效先于结论。** 经验必须带证据定位（提交、代码行、测试、文档），并锚定到文件和函数符号。代码一变，相关经验自动进入待复核；只格式化或改注释不会误报。
5. **AI 提议，人来裁决。** 新经验先进试用期，有人确认才转正；规则文档和词表的修改只能由 AI 提议、人确认后写入。对团队规范的例外必须带批准人和到期日。
6. **克制地占用注意力。** 每层注入都有 token 预算（常驻规则 500、回合提醒 300、文件护栏 240），常驻部分字节级稳定以保住 KV 缓存；不确定相关的宁可不提。
7. **自我改进，但每一步可见、可撤销。** 检索参数会根据反馈自动调整并自动回滚；低效经验会自动降级。但知识内容本身从不自动改写——自动改错的代价，远大于知识库长得慢。

## 核心架构

AccreMind 分成三个包：内核 `@accremind/core` 不依赖任何宿主，插件 `@accremind/dsh-plugin` 只负责接入 DSH，工作台 `@accremind/webui` 构建为单文件内联进插件。内核只用 Node 24 标准库（内置 `node:sqlite`），没有第三方运行时依赖。

&#91;embedded content: AccreMind 的三层结构 · 宿主、插件、内核、存储\]

这样分层的好处：换一个宿主（其他 IDE 插件、服务端）只需要重写接入层；索引损坏或升级时从 Markdown 卡片重建即可，不会丢知识。

AI 在三个时刻拿到经验，各有独立的预算：

| 时刻 | 层 | 默认预算 | 给什么 |
| --- | --- | --- | --- |
| 每轮对话开头 | 常驻规则 | 500 tokens | 团队硬约束和项目概况，字节稳定以保住 KV 缓存 |
| 每轮按提问检索 | 回合提醒 | 300 tokens | 相关经验的编号和一句摘要、相关文档章节 |
| 读写相关文件时 | 文件护栏 | 240 / 1500 tokens | 该文件上的高风险经验；需要时展开全文 |

遇到的问题与解决方案、技术选型、详细架构、亮点和同类产品对比，见 详细设计与对比。

## 一条经验的一生

经验从信号到正式要过两道关：增量评估（代码里已经有的不收）和试用期（没人确认的不转正）。转正之后，反证、代码变化和使用反馈会继续改变它的状态。

&#91;embedded content: 一条经验的状态变化 · 8 个状态，一条自动降级回路\]

所有状态变化都由同一张生命周期表定义，不管是人点按钮、AI 登记反馈还是后台巡检触发，规则都一样。每次变化都写进活动日志，并同步到 Markdown 卡片，在 Git 里可以看到。

## 五层知识与跨仓库共享

每条经验属于五层之一。层决定它存在哪、谁能看到、以什么门槛出现在别的仓库里。一条经验只写一次，按相关性在本机所有仓库之间命中。

| 层 | 存放位置 | 谁能看到 | 典型内容 |
| --- | --- | --- | --- |
| 团队规范 `team_rule` | 仓库 `.accremind/rules/`，随 Git 共享 | 整个团队，每轮常驻且优先 | 错误码规范、必须走的审计日志 |
| 业务领域 `domain` | 仓库内，或本机共享区 | 同一业务领域的所有仓库 | 退款精度规则、对账口径 |
| 通用技术 `shared_tech` | 本机 `~/.dsh/accremind/` | 技术栈匹配的仓库（语言、依赖、版本范围） | 某库 3.x 的 SSR 陷阱 |
| 项目 `project` | 仓库 `.accremind/entries/` | 本仓库；其他仓库只在显式要求时作参考 | 这个服务的重试策略为什么这样定 |
| 个人 `personal` | 本机，归属于用户 | 只有本人，跨仓库 | 我的调试习惯和常用排查路径 |

跨仓库共享靠三件事保证不"串味"：

- **稳定的仓库身份**：优先取已提交的 `.accremind/repo.json`，其次 Git `origin`，最后才是路径。换个目录克隆，经验不丢。
- **适用性闸门**：先判断"这条经验凭什么适用于这里"（本仓库 / 同领域 / 同技术栈 / 本人 / 跨仓库参考），每种有自己的相关性门槛和名额。
- **分作用域的反馈**：共享经验在某个仓库被标"不适用"，只在该仓库停止提醒；多个仓库都这样、或任一仓库报告反例，才全局暂停。

## 检索：在对的时候递到手边

检索的目标不是"找到最多"，而是"只递对的那几条"：每轮提醒只有约 300 token 的位置，一条无关提醒就会挤掉一条有用的。

一次检索按顺序经过这些步骤：

1. **补足信号**：宿主常常只给一句用户原话。会话首轮会补上工作区未提交的改动文件和分支名（`feature/refund-partial` → "退款"）。
2. **打主题标签**：问题和经验用同一套受控词表打标签，没有共同字词也能命中（"重复扣款"和"幂等键"都是"支付幂等"）。有模型时，首轮和换话题时请模型理解后打标签，1.5 秒超时就退回词表匹配；词表里没有的新词进入待确认。
3. **SQL 预筛**：先用适用性条件在数据库里筛掉不可能相关的条目（与本仓库无关的个人经验、无关领域），再打分。
4. **多信号打分**：全文（FTS5 trigram，支持中文）、别名、文件路径、符号、主题标签加权。
5. **适用性闸门 + 名额**：每种适用理由各有门槛和名额，跨仓库参考至少要两个独立信号。相似条目按簇去重。
6. **规范优先**：与团队规范相反、又没登记豁免的条目会标注"以规范为准"，并进入治理队列。

**规则文档集**是另一个知识来源。业务领域、业务规则、项目规范、项目基本业务属性四类文档放在 `.accremind/docs/`，可以手动导入。文档按章节建索引，相关章节随提醒一起给 AI，项目概况常驻。开发过程中 AI 发现缺漏只能提议修改，人确认后写入，每次改动都记入变更明细。

在 30 个仓库、一万条经验的压测下，单次检索 p95 约 60–90 ms，文件护栏 p95 约 1.5 ms。

## 自我改进

AccreMind 会自己变好，但只自动做两件低风险的事：调整检索参数、退回低效经验。经验内容、团队规范和规则文档仍然是"AI 提议、人确认"。

**自动调参**用检索反馈里的"有用 / 不适用"作为评测集，回放提醒、寻找更好的参数。得分 = 召回率 − 被否定条目的出现率 − ½ × 无关问题的噪声率。

&#91;embedded content: 自动调参 · 护栏、观察期与回滚\]

**低效经验自动降级**的触发条件：

| 步骤 | 条件 | 结果 |
| --- | --- | --- |
| 降为试用 | 当前版本被 ≥ 2 个会话标"不适用"，占提醒会话 ≥ 25%，且无任何确认 | 仍会提醒，但受试用次数限制；有人确认就自动转回正式 |
| 降为试用 | 30 天内在 ≥ 40 个会话中提醒过，从未被打开、引用或确认 | 同上 |
| 自动归档 | 因"不适用"暂停后 30 天无人处理（试用期满无人决定的等 60 天） | 停止提醒，清理待办队列 |

团队规范、当前版本有过确认或反例的、跨仓库共享的经验不做自动处理。每一步都会出现在工作台的"需要你处理"里，可以一键撤销；撤销后这个版本不再被自动降级。

## 怎么开始用

安装后日常使用几乎不需要额外动作：照常在 DSH 里和 AI 写代码，偏一下眼回合末尾的回执，点"有用 / 不适用 / 不准"即可。

**安装（Node.js ≥ 24，pnpm 10）**

```bash
pnpm install
pnpm verify                  # 构建 + 全部测试 + 工作台产物校验
pnpm install:dsh             # 把插件链接进 DSH，重启 DSH 生效
```

**第一周建议这样用**

1. **设置业务领域**：`pnpm accremind repo --domains payment,settlement`，提交生成的 `.accremind/repo.json`。
2. **冷启动**：`pnpm accremind bootstrap --top 10` 从 Git 历史里找回滚、排障、竞态类的高信号提交，配置模型后可加 `--extract` 提炼候选。
3. **导入规则文档**：`pnpm accremind docs import ./docs/refund.md --category business_rules`。
4. **日常开发**：AI 会在改动前看到相关经验；踩到新坑时让它调用 `accremind_capture` 提交候选。
5. **每周花 10 分钟治理**：打开工作台（`pnpm ui`），处理"需要你处理"里的候选、试用期满、待复核和自动降级。
6. **提交共享**：把 `.accremind/` 下的正式经验、规则、文档和词表随代码一起提交评审。

**AI 在对话里能用的工具**

| 工具 | 用途 |
| --- | --- |
| `accremind_search` | 按关键词、层、文件路径检索经验和文档章节 |
| `accremind_get` | 取完整正文、前置条件、验证方法和证据 |
| `accremind_capture` | 提交经验候选，走五路分流 |
| `accremind_validate` | 登记本次使用的成败，失败会立即暂停该条 |
| `accremind_propose_doc_change` | 提议修改规则文档，等人确认 |
| `accremind_export_skill` | 把已验证的经验导出为 DSH 技能文档 |

## 边界与常见问题

**数据会离开我的电脑吗？** 默认不会。检索、提醒、文件护栏、时效巡检全部在本机完成。只有"提炼经验"会调用模型，默认复用 DSH 宿主的模型服务；对话结束后的自动提炼默认关闭，开启后发送的也是脱敏片段。

**工作台安全吗？** 只监听 `127.0.0.1`，每次启动生成一次性令牌，跨站和无令牌请求一律拒绝。

**经验错了怎么办？** 任何人在回执里点"不准"，或 AI 登记一次失败，这条经验立即暂停提醒，进入治理队列等人处理。

**会不会越用越吵？** 不会。每层有固定 token 预算；经常不适用或从来没人用的经验会自动降级。

**和写文档、写 Wiki 有什么不同？** 文档是给人主动去查的；AccreMind 在 AI 要动相关代码的那一刻主动递过去，并且会因为代码变化而自己标记过期。规则文档集可以直接从现有文档导入。

**它不做什么**

- 不替代代码评审、测试和文档，只补它们覆盖不到的那一层。
- 不自动改写经验内容和规则文档。
- 不给 AI 下命令，只提供参考。
- 目前不带中心服务器，团队共享走 Git。
