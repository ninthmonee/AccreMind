- 版本：2.1（阶段 A 契约修订）；日期：2026-09-12。
- 依据：[AI 研发知识基座 PRD V2.1](<../../AI 研发知识基座 PRD V2 修订版.md>)。
- 状态：实施设计建议。本文规定模块、契约和验收边界，不表示系统已实现或评测已通过。
- 文档协作：[工具端架构](<../../docs/architecture/01-工具端架构设计.md>) · [前端架构](<../../docs/architecture/02-前端架构设计.md>) · [后端架构](<../../docs/architecture/03-后端架构设计.md>) · [开发任务与验收计划](<../../docs/architecture/04-开发任务与验收计划.md>)。
- 规则优先级：PRD V2.1 为产品依据；跨端契约以随附 OpenAPI/JSON Schema 和《后端架构》B10—B20 的详细规则为实现基线；B1—B9 为概要导航。发现冲突须先修正契约与文档，不能自行选择较宽松规则。

## P1. 目标、范围与完成定义

目标是按工具端、前端、后端三条工作线，交付 PRD V2.1 的最小可用闭环：显式提交 → 可发现性与增量判定 → 五路分流 → 人工审核 → 授权检索 → 使用与验证 → 纠错撤回。

本文件是待执行任务清单，不代表开发已开始。以下任务初始状态均为待开始，责任人先列角色；默认技术栈与宿主按详细设计执行；具体人员、环境参数、精确依赖锁文件及工期在 D00 确认。工程优先级“必需/后置”和知识候选的 P0/P1/P2 是不同概念。

MVP 不要求自动全会话采集、向量检索、图数据库、多宿主、自动发布或远程接管。人工 CaptureAssessment 必须可用；后端 LLM 用于辅助提炼，不能替代证据和发布门槛。

单任务完成必须同时具备：代码或约定产物、对应契约更新、必要的验收证据、已知限制与可复现说明。仅提交 Prompt、Mock 演示、页面截图或“模型自评通过”不能证明关键能力完成。

## P2. 工程组织与契约先行

建议采用一个代码库：apps/tool、apps/web、apps/api、apps/worker、packages/contracts、packages/domain、tests/contract、tests/e2e、evals、ops。apps/worker 属于后端，数据库与存储也归后端维护；不新增第四条产品维度。

D01 产出机器可校验的 HTTP schema、MCP 工具定义、统一枚举、fixtures 和错误结构。后端架构 B10—B20 为详细实现依据，B4—B7 仅作概要导航。前端和工具端从共享契约生成客户端，禁止分别复制字段。并行开发可以使用 fixtures，联调时不得继续用 Mock 替代后端规则。

共同版本策略：兼容新增字段允许次版本演进；删除字段、修改状态语义、改变发布必填项需显式契约升级、迁移方案与三端兼容验收。协议库、运行时和模型版本在 D00/D01 后锁定并记录，不使用未固定的“latest”作为交付依据。

## P9. 依赖与执行顺序

关键的人工知识闭环路径：D00 → D01 → B01 → B02 → B03 → B05 → B06 → B07 → T03/F03。自动提炼 B04 可在 B03 后开展，人工判定不必等待模型检查器。

可以并行的工作线（不表示本文已自动启动任何开发任务）：

- D01 后：工具 T01、前端 F01、后端 B01、测试 Q01 的样本工作。
- B02 后：配置 B09 与贡献 B03。
- B03 后：提炼 B04 与人工判定 B05；T04/F02 在所需接口就绪后联调。
- B06 后：检索 B07、验证 B08；B08 完成后治理 B10。
- 前端/工具可先用冻结 fixtures 开发，但依赖的真实接口验收是任务完成前提。
- T06 完成后才能将长生命周期 Bridge 用于真实证据；F06/F07 完成后才允许多人执行生产审核。

团队若只有少量开发者，可按纵向切片交付：登录绑定 → 手工导入并判定 → 审核发布 → 工具检索 → 提炼与提交 → 验证纠错。不得为了先出搜索 Demo，把增量判定移出 MVP。

## P11. 验收门槛与证据格式

沿用 PRD V2.1 建议门槛，试点启动前冻结：

- 已发布条目的必要字段、owner、来源、合法判定及经验增量证据绑定覆盖率 100%；已知越权或无依据确定性断言发布用例不得出现失败。
- 60 条查询样本包含 30 可回答、15 无答案、10 条件冲突、5 权限隔离；权限样本不代替完整授权矩阵。
- 有答案样本宏平均 Precision@5≥80%、Recall@5≥70%；有答案却返回零条时两者按 0 计。无答案误返回率≤10%；已知不兼容建议不能作为直接建议。
- 至少 20 条候选标注样本五类分流各≥4，额外覆盖镜像、预算耗尽、缺权限、猜中无依据、混合结论及根因不明。
- 1000 条知识、10 并发，端到端 P95≤2 秒、错误率≤1%；记录中文处理方式、模型/索引/宿主版本与网络。提炼延迟另计。
- 真实任务至少 20 个；耗时中位数改善 15% 且返工不增加只是待验证收益假设，报告样本限制，不将其包装为已证明收益。
- 恢复建议 RPO 24 小时、RTO 4 小时；实际数据缺口与恢复耗时通过演练记录。

每份验收报告应含：任务/用例 ID、代码版本、契约版本、配置/模型版本、数据集版本、环境、步骤、预期与实际、通过/失败、request_id/job_id/knowledge_revision、脱敏证据链接、限制与后续负责人。

失败不靠改阈值消除；有明确合理原因调整目标时，记录决策与新一轮评测版本。代码覆盖率或知识数量不能替代业务验收。
